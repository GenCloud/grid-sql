# Практические советы

Правила, которые делают работу Grid предсказуемой: размещение данных на диске, доступ, восстановление, мониторинг, схема и работа клиентов. Тот же материал в виде контрольного списка перед вводом в эксплуатацию — в [чек-листе](production-checklist.md).

## Порядок на запуске

1. Настройте пробы Actuator **liveness** и **readiness** (`/health/*` в starter) — трафик только после readiness UP ([мониторинг](../configure-and-operate/monitoring.md)).
2. Ограничьте SQL-порт, создайте первого администратора, выдайте `GRANT` приложениям ([безопасность](../configure-and-operate/operations/security.md)).
3. Убедитесь, что клиенты закрепляются на `writerEligible` и обрабатывают `PROMOTE_NOTIFY` / `rediscoverWriter()` ([повышение роли](../configure-and-operate/operations/ha-promote.md)).
4. Включите `oplog-archive`, снимите base, отработайте офлайн-restore ([PITR](../configure-and-operate/operations/pitr.md), [резервное копирование](../configure-and-operate/operations/backup-restore.md)).
5. Перед вводом в эксплуатацию прогоните drill повышения роли на стенде ([отказы](../configure-and-operate/operations/failures.md)).

## Эксплуатация

- **Отдельный `dataDir` на каждый узел**, на локальном диске. Общий каталог или том NFS/SAN на весь кластер не поддерживаются.
- Долговременное хранение и репликация включаются **раздельно**: одиночный узел может писать на диск без реплик. На каждом таком узле держите `fsync: true` для журнала.
- **Пользователи и аутентификация** — до того, как к SQL-порту получит доступ сетевое приложение: [безопасность](../configure-and-operate/operations/security.md).
- **Восстановление:** включите архив журнала (`oplog-archive`) заранее, снимайте базовые копии по расписанию и отрабатывайте восстановление на копии: [PITR](../configure-and-operate/operations/pitr.md).
- **Пробы Actuator** (liveness и readiness) должны быть настроены до подачи трафика: [мониторинг](../configure-and-operate/monitoring.md).
- **Сценарии отказов** — потеря пишущего узла, рассинхронизация ORCHID, проблемы между ЦОД, отставшая реплика: [отказы](../configure-and-operate/operations/failures.md).
- **Смена версии бинарника** — поэтапный перезапуск с тем же `dataDir`: [обновление узла](../configure-and-operate/operations/upgrade.md).
- Клиенты в HA-конфигурации закрепляются на узле с признаком `writerEligible` и следуют подсказкам `ServerMeta` / `PROMOTE_NOTIFY`: [повышение роли узла](../configure-and-operate/operations/ha-promote.md).
- Чтение собственных записей через реплику не гарантируется: [чтение с реплики](../configure-and-operate/operations/replica-reads.md).
- Автоматический перенос шардов (`apply-auto-cutover`) включён по умолчанию; его отключение — временная мера: [overlay и размещение](../understand/overlay-and-swarm.md).

## Частые ошибки

| Ошибка | Как правильно |
|--------|---------------|
| Общий `dataDir` на два процесса | Отдельный каталог на каждый узел, на локальном диске |
| JDBC как источник нагрузки в JMeter и замерах ёмкости | JMeter по `grid://`; JDBC — для сервисов и IDE |
| Перебор следующего хоста в URL после смены пишущего узла | `rediscoverWriter()` или ожидание `PROMOTE_NOTIFY` |
| Публикация цифр, снятых с `fsync: false` | Мерить и публиковать только с `fsync: true` |
| Включить архив журнала «потом» | Включить до той нагрузки, которую может потребоваться откатить |

## Схема и запросы

- Индексы объявляйте средствами SQL DDL. Битовые индексы — только явным `CREATE BITMAP INDEX`.
- Составной индекс даёт выигрыш, когда фильтр совпадает с префиксом его колонок.
- Проверяйте план запроса: `EXPLAIN` — [EXPLAIN и AQE](../sql/explain-and-aqe.md).
- DDL внутри открытой транзакции отклоняется: меняйте схему в режиме autocommit.
- Не используйте `SELECT *` на горячих путях.

## Приложения

- Выбирайте один интерфейс под стек: реактивный (`grid://`) или JDBC (`jdbc:grid://`). Оба стабильны: [JDBC-клиент](../develop/jdbc-tooling.md).
- Одна `ConnectionFactory` на процесс; при остановке вызывайте `dispose()`.
- Параллельные транзакции — это несколько объектов `TxContext` на одном TCP-соединении.
- `.block()` допустим только на границе приложения (`main`, CLI, тесты).
- Не держите транзакцию открытой на время вызова во внешнюю систему.
- Большие выборки читайте окнами: [потоковая выдача](../develop/wire-streaming.md).

## Измерения

Мерьте только с `fsync: true`. Режим `fsync: false` нужен, чтобы локализовать узкое место в лаборатории, и не является заявленным максимумом.

Запускайте по одной проверке за раз на незагруженном хосте: параллельные проверки обесценивают результат. Порядок внутренних прогонов описан в [методике](../performance/methodology.md).

Ссылайтесь на JSON конкретного прогона: [ёмкость и пороги](../performance/capacity-slo.md), [результаты](../performance/results.md). Пороги — это нижняя граница регресса, около 95% планового значения, а не цель для разгона. Нагрузку подавайте JMeter по `grid://`: [нагрузка и SLO](../tools/jmeter-load-slo.md).

## Чего ожидать от производительности

Запись упирается в допуск ORCHID и журнал, а не в свободный процессор. Чтение масштабируется примерно на порядок лучше записи — это ожидаемая картина. Запас по чтению дают реплики, а не увеличение числа потоков записи.
