# Зачем Grid

Часто берут дисковую SQL-СУБД «на всегда» и рядом — кэш в памяти «на горячее». Получаются два клиента, два контура отказа и вечный вопрос: кэш уже обновили, а журнал ещё нет?

Grid собирает это в один продукт: горячие данные в памяти, надёжная запись сначала в журнал на диске, согласование узлов протоколом ORCHID, один протокол для приложений — `grid://` (реактивный) или `jdbc:grid://` (JDBC).

## Одна система вместо связки

В Grid схема, транзакции, память и диск — не четыре сервиса, а один контур:

- SQL DDL/DML и каталог таблиц;
- горячий набор в RAM поверх запечатанных файлов и журнала OpLog;
- кластерная запись, которую ORCHID допускает **до** видимости строки;
- один протокол для всех сервисов.

Меньше подвижных частей — меньше мест, где слои разъехались.

## Долговременное хранение и репликация — разные рычаги

| Переключатель | Что даёт |
|---------------|----------|
| `grid.durability.enabled` | Локальный ORCHID + OpLog + запечатанные файлы; один узел без соседей — штатный режим |
| `grid.replication.enabled` | Доставка журнала соседям, кворум, подтягивание, ремонт |

Включайте независимо. Подробнее: [долговременное хранение](../configure-and-operate/configuration/durability.md), [репликация](../configure-and-operate/configuration/replication.md).

## Запись, которой можно доверять

При включённой записи на диск строка видна **после** журнала и согласия по контрольным суммам, не по схеме «сначала в память». Сбой на шаге — ошибка клиенту, без частично применённой строки. Лучше отказ, чем два журнала.

Отсюда: `fsync` на рабочих профилях; один пишущий узел (выбор по фазе); смена роли через `ServerMeta` / `PROMOTE_NOTIFY`, без ручного перебора хостов в URL.

Дальше: [обзор архитектуры](../understand/architecture-overview.md), [ORCHID](../understand/orchid-consensus.md), [повышение роли](../configure-and-operate/operations/ha-promote.md).

## Скорость там, где горячий набор

Память ускоряет горячие ключи; весь объём в RAM класть не нужно. Холодные ключи лежат в запечатанных файлах и подгружаются при промахе. Запросы — SQL, индексы B+ и битовые; тяжёлые SELECT — адаптивно (AQE).

Ориентиры на лабораторном хосте (два узла, `fsync: true`): [ёмкость и пороги](../performance/capacity-slo.md). Снимали на том же `grid://`, что у приложений.

## От одного узла до нескольких площадок

Один узел с диском (`capacity`), пара 1+1, кольцо из трёх, Active/Hold между ЦОД, `ASYNC_SHIP` и `SYNC_VOTERS` — одна модель данных.

Размещение шардов и PIN — поверх той же репликации: [overlay и размещение](../understand/overlay-and-swarm.md).

## Клиент без сюрпризов протокола

Один протокол, много логических сессий на одном TCP: у клиента `maxTxContexts` по умолчанию **256**, на сервере жёсткий потолок канала **8** (Boot не поднимает из YAML). Потоковая выдача, `PREPARE`. Без второго протокола рядом с Grid.

См. [Java-клиент](../develop/java-client.md), [подключение клиентов](connect-clients.md).

## Чего в продукте нет

- Два пишущих сразу и слияние их журналов.
- Общий `dataDir` на NFS/SAN на весь кластер.
- TLS на SQL-порту в поставке — терминация снаружи; [безопасность](../configure-and-operate/operations/security.md).
- Гарантия «сразу увидеть свою запись» через отстающую реплику без обращения к пишущему.
