# Зачем Grid

Grid держит горячие данные в памяти, пишет надёжно — сначала в журнал на диске, согласует узлы протоколом ORCHID и предоставляет приложениям один протокол `grid://`. Часто начинают с дисковой СУБД плюс отдельный кэш в памяти; ниже — что даёт объединение этих слоёв в один продукт.

## Одна система вместо связки

Дисковая SQL-СУБД для надёжности и отдельный кэш для горячего чтения означают двух клиентов, два контура отказа, расхождение кэша и базы, а также раздельную эксплуатацию каждого слоя.

В Grid схема, транзакции, память и диск — один продукт:

- SQL DDL/DML и каталог таблиц;
- рабочий набор в оперативной памяти, опирающийся на запечатанные файлы и журнал OpLog на диске;
- кластерная запись, допускаемая ORCHID до того, как строка станет видимой;
- один протокол для приложений: `grid://` (реактивный API) или `jdbc:grid://` (JDBC).

Меньше подвижных частей — меньше ситуаций, когда кэш уже обновлён, а журнал ещё нет.

## Долговременное хранение и репликация — разные рычаги

| Переключатель | Что даёт |
|---------------|----------|
| `grid.durability.enabled` | Локальный ORCHID + OpLog + sealed; одиночный узел без пиров — штатный режим |
| `grid.replication.enabled` | Доставка журнала на соседей, кворум, подтягивание, repair |

Включайте их независимо. Подробнее: [долговременное хранение](../configure-and-operate/configuration/durability.md), [репликация](../configure-and-operate/configuration/replication.md).

## Запись, которой можно доверять

При включённом долговременном хранении строка становится видимой **после** записи в журнал и получения кворума по контрольным суммам, а не по схеме «сначала в память, потом на диск». Отказ на любом шаге возвращается клиенту как ошибка и не оставляет частично применённых изменений.

Отсюда:

- `fsync` и групповой сброс журнала на рабочих профилях `primary` / `replica`;
- единственный пишущий узел в каждый момент времени (выбор по фазе), без слияния изменений двух мастеров;
- передача роли пишущего средствами самого протокола (`ServerMeta` / `PROMOTE_NOTIFY`), без ручного перебора хостов в URL.

Подробнее: [обзор архитектуры](../understand/architecture-overview.md), [ORCHID](../understand/orchid-consensus.md), [повышение роли узла](../configure-and-operate/operations/ha-promote.md).

## Скорость там, где горячий набор

Память ускоряет рабочий набор, но весь объём данных помещать в неё не требуется. Холодные ключи лежат в запечатанных файлах и подгружаются при промахе. Запросы остаются SQL и обслуживаются индексами B+ и битовыми (*bitmap*), а тяжёлые SELECT выполняются адаптивно (AQE).

Ориентиры пропускной способности для лабораторного хоста (два узла, `fsync: true`) и условия, в которых они получены, — в [ёмкости и порогах](../performance/capacity-slo.md). Измерения сделаны на том же стеке, что используют приложения: `grid://` с включённым долговременным хранением.

## От одного узла до нескольких площадок

Одиночный узел с записью на диск (`capacity`), пара 1+1, кольцо из трёх узлов, схема Active/Hold между площадками, режимы `ASYNC_SHIP` и `SYNC_VOTERS` — один и тот же продукт и одна и та же модель данных.

- [запуск кластера](start-cluster.md)
- [HA в одном ЦОД](../configure-and-operate/operations/cluster-ha-highload.md)
- [несколько ЦОД](../configure-and-operate/operations/multi-dc.md)

Размещение шардов и закрепление ключей (PIN) — дополнительные рычаги поверх той же репликации: [overlay и размещение](../understand/overlay-and-swarm.md).

## Клиент без сюрпризов протокола

Приложения работают через `grid://` и `ConnectionFactory` либо через JDBC (`jdbc:grid://`): один протокол продукта, множество логических сессий на одном сокете (`maxTxContexts` — у клиента **256**, на сервере **8**), потоковая выдача результатов, `PREPARE`. Один стек драйвера для приложений — без второго протокола рядом с Grid.

См. [Java-клиент](../develop/java-client.md), [подключение клиентов](connect-clients.md), [возможности](features.md).

## Что остаётся вне продукта

- Два пишущих сразу и слияние их журналов.
- Общий `dataDir` на NFS/SAN на весь кластер — каталог принадлежит одному узлу.
- TLS на SQL-порту в поставке нет — терминация снаружи (прокси / балансировщик); см. [безопасность](../configure-and-operate/operations/security.md).
- Read-your-writes через отстающую реплику без обращения к writer.

## Когда Grid — правильный выбор

| Нужно в одном продукте | Grid закрывает |
|------------------------|----------------|
| SQL, транзакции, горячая память и диск | Да |
| Кластерная запись с журналом до видимости строки | ORCHID, OpLog и запечатанные файлы |
| Один протокол для всех сервисов | `grid://` |
| HA и несколько площадок без смены модели данных | 1-DC / Active–Hold / `ASYNC_SHIP` · `SYNC_VOTERS` |
| Измерения на том же протоколе, что и у приложений | [ёмкость и пороги](../performance/capacity-slo.md) |
