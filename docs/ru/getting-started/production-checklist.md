# Чек-лист перед промышленной эксплуатацией

Что нужно решить до того, как кластер Grid примет промышленный трафик. В каждом пункте указаны настройка или команда, причина и страница с полной процедурой. Проходите список сверху вниз: хранение, кластер, восстановление, доступ, наблюдаемость, клиенты.

## 1. Хранение и надёжность записи

| Проверка | Настройка | Зачем |
|----------|-----------|-------|
| Долговременное хранение включено на каждом узле, который должен пережить перезапуск | `grid.durability.enabled: true` | Запись проходит через ORCHID и журнал изменений (*OpLog*) **до** того, как станет видимой; при сбое фиксация отменяется, а не остаётся применённой наполовину |
| `fsync` для журнала | `grid.replication.op-log.fsync: true` | Без него подтверждённые непосредственно перед аварией фиксации могут быть потеряны. `fsync: false` — лабораторный приём для локализации узкого места |
| Отдельный `dataDir` на каждый узел, на локальном диске | `grid.replication.op-log.data-dir`, `dataDir` узла | Два процесса в одном каталоге или том NFS/SAN на весь кластер разрушают сегменты журнала и запечатанные файлы |
| Режим прогрева выбран под объём данных | `grid.durability.hydrate-mode: LAZY` | `LAZY` отображает запечатанные файлы и подтягивает ключи при промахе — обычный промышленный выбор. `FULL` загружает всё сразу и на большом объёме замедляет старт вплоть до нехватки памяти |
| Задан предел рабочего набора | `grid.durability.working-set-max-entries` | Ограничивает память вытеснением холодных зафиксированных ключей; незафиксированные и промежуточные записи не вытесняются |
| Есть запас места под журнал, запечатанные файлы и архив | — | Усечение журнала идёт только до отметки запечатывания, а при включённом архиве неудачное копирование отменяет усечение |

Подробно: [долговременное хранение](../configure-and-operate/configuration/durability.md), [хранение](../understand/storage-sealed-gmap.md).

## 2. Кластер и единственный пишущий узел

| Проверка | Настройка | Зачем |
|----------|-----------|-------|
| Долговременное хранение и репликация выбраны раздельно | `grid.durability.enabled`, `grid.replication.enabled` | Одиночный узел с записью на диск — поддерживаемый режим; репликация добавляет к нему доставку на соседей, кворум и подтягивание |
| На каждом узле заданы `node-id`, `cluster-id`, `transport` и `peers` | YAML узла | Профили starter демонстрационные, а чужой `cluster-id` блокирует подтягивание |
| Пишущий узел ровно один | — | Пишет только выбранный по фазе узел; слияния изменений двух мастеров не существует |
| Клиенты берут пишущий узел из метаданных протокола | `ServerMeta`, `PROMOTE_NOTIFY` | HTTP-проверки здоровья предназначены оркестратору, а не поиску пишущего узла |
| Порты SQL и репликации разведены | SQL **15432** / **15433**, репликация **5615** / **5616** | Клиент, попавший на порт репликации, получит `bad frameLen …` |
| Для нескольких площадок проверены роли регионов и кворум | `grid.replication.region.*` | Разграничение Active/Hold и кворум заявок определяют, кому разрешено писать после потери площадки |

Подробно: [репликация](../configure-and-operate/configuration/replication.md), [повышение роли узла](../configure-and-operate/operations/ha-promote.md), [несколько ЦОД](../configure-and-operate/operations/multi-dc.md).

## 3. Резервные копии и восстановление

| Проверка | Настройка или инструмент | Зачем |
|----------|--------------------------|-------|
| Архив журнала включён **до** первой нагрузки, которую может потребоваться откатить | `grid.durability.oplog-archive.enabled: true`, отдельный `dir` на каждый узел | Включение архива во время инцидента не даёт ничего, из чего можно восстановиться |
| Базовые копии снимаются по расписанию | `SealedBaseBackupUtil` | Для восстановления нужны запечатанная база на отметке `W` и сегменты архива `[W+1 … T]` |
| Покрытие архива проверяется после усечения журнала | — | Если архив не покрывает хвост после `W`, восстановление до `T` остановится раньше времени |
| Восстановление отработано офлайн на копии `dataDir` | `PitrRestoreMain --until-seq` | Тренироваться на работающем пишущем узле нельзя. Неудачная тренировка — дефект эксплуатации, который надо устранить до настоящего инцидента |
| Восстановление между площадками защищено ограждением | `PitrCoordinatedRestore`, `PitrActiveFence` | Одновременное восстановление всех площадок грозит появлением двух пишущих узлов |

Подробно: [PITR](../configure-and-operate/operations/pitr.md), [резервные копии и восстановление](../configure-and-operate/operations/backup-restore.md).

## 4. Доступ и сеть

| Проверка | Действие | Зачем |
|----------|----------|-------|
| SQL-порт доступен только из доверенных сетей | Межсетевой экран или балансировщик перед **15432** | Пока каталог пользователей пуст, администратора может создать любой, кто дотянулся до порта |
| Первый администратор создан до подачи трафика | `CREATE USER admin PASSWORD '…'` | Как только пользователь существует, кадры без аутентификации отклоняются |
| Пользователи приложений получают минимально необходимые права | `GRANT` и `REVOKE` на схему и таблицы | Права проверяются с обеих сторон соединения JOIN |
| TLS терминируется перед узлом | Обратный прокси или балансировщик | Продукт не обслуживает TLS на SQL-порту |
| Репликация остаётся каналом между узлами | **5615** / **5616** | Транспорт репликации — другой протокол, публиковать его наружу нельзя |
| Согласована процедура смены учётных данных | `ALTER USER … PASSWORD`, затем обновление URL приложений | Открытые сессии сохраняют прежние права до переподключения |

Подробно: [безопасность](../configure-and-operate/operations/security.md).

## 5. Наблюдаемость

| Проверка | Конечная точка или метрика | Зачем |
|----------|----------------------------|-------|
| Настроена проба живости | `/health/liveness` (`gridLiveness`) | Процесс и исполнитель логики живы |
| Настроена и учитывается проба готовности | `/health/readiness` (`gridReadiness`) | SQL-порт слушает, а при включённой репликации ORCHID синхронизирован. Неготовый узел не должен принимать трафик |
| Настроен сбор метрик Prometheus | `/prometheus` | `grid.replication.orchid_r`, `repair_issued` и `repair_applied`, `rpo_estimate_ms` |
| Определены оповещения | См. ниже | Сигналы, предшествующие отказу |
| Понятно разделение стадий записи | `orchidWaitP99Ns` против `oplogFsyncP99Ns` | Рост ORCHID указывает на сеть между узлами или порог `R`, рост fsync — на диск |

Оповещайте как минимум на: readiness DOWN после прогрева; `applyLagStale: true` на реплике для чтения; `orchid_r` ниже порога допуска записи; рост задержки fsync журнала или нехватку места на диске; рост `repair_issued` без соответствующего роста `repair_applied`.

Подробно: [мониторинг](../configure-and-operate/monitoring.md), [отказы](../configure-and-operate/operations/failures.md).

## 6. Клиенты

| Проверка | Действие | Зачем |
|----------|----------|-------|
| Одна `ConnectionFactory` на процесс, освобождается при остановке | `factory.dispose()` | Одно TCP-соединение несёт множество транзакций, пул сокетов ничего не добавляет |
| Задан бюджет параллелизма | `maxTxContexts` | В URL клиента по умолчанию **256**; на сервере жёсткий потолок **8** на TCP (при исчерпании — ещё один `Connection`) |
| Смена пишущего узла обрабатывается средствами протокола | `rediscoverWriter()`, `PROMOTE_NOTIFY` | Перебор следующего хоста в URL после отказа грозит попаданием на непишущий узел или на устаревшую эпоху региона |
| Таймауты и повторы заданы явно | `connectTimeoutMs`, `execTimeoutMs`, `retryMode` / `maxRetries` | По умолчанию `execTimeoutMs` выключен, а повторы отключены |
| Семантика чтения с реплики принята там, где оно включено | `readEndpoints`, `readPreference` | Чтение собственных записей через реплику не гарантируется, а устаревшее чтение отклоняется |
| Большие выборки читаются окнами | `fetchWindow` | Не даёт материализовать весь результат на стороне клиента |
| `.block()` допустим только на границе приложения | `main`, CLI, тесты | Блокировка внутри реактивного конвейера останавливает цикл событий |

Подробно: [подключение клиентов](connect-clients.md), [Java-клиент](../develop/java-client.md), [чтение с реплики](../configure-and-operate/operations/replica-reads.md).

## 7. Управление изменениями

| Проверка | Действие | Зачем |
|----------|----------|-------|
| Обновление версии — поэтапный перезапуск с тем же `dataDir` | [обновление узла](../configure-and-operate/operations/upgrade.md) | Данные остаются на диске, узел восстанавливает состояние из запечатанных файлов и журнала |
| Изменения схемы выполняются в autocommit | — | DDL внутри открытой транзакции отклоняется |
| Автоперенос шардов оставлен включённым, если нет причин обратного | `apply-auto-cutover` | Отключение — временная мера: [overlay и размещение](../understand/overlay-and-swarm.md) |
| Цифры ёмкости сняты с `fsync: true` на незагруженном хосте | [ёмкость и пороги](../performance/capacity-slo.md) | Значения без fsync или полученные при параллельных проверках не годятся для планирования |

## Проверка перед вводом в эксплуатацию

Перед первой промышленной записью убедитесь: долговременное хранение включено, `fsync: true`; `dataDir` локальный и отдельный на каждый узел; пишущий узел один, клиенты закрепляются по `ServerMeta` / `PROMOTE_NOTIFY`; аутентификация включена, права выданы по минимуму; архив журнала работает, базовая копия снята, восстановление отработано; пробы живости и готовности настроены, оповещения заведены.
