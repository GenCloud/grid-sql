# Резервное копирование и восстановление

Как защитить узел с долговременным хранением и вернуть его после сбоя. Точка во времени и ключи архива: [PITR](pitr.md). Раскладка на диске: [долговременное хранение](../configuration/durability.md).

## Что копировать

На каждом узле — **локальный** `dataDir` (не общий NFS/SAN на весь кластер):

| Артефакт | Роль |
|----------|------|
| Запечатанные файлы карты (`.gmap`) | Уплотнённое хранилище ключ → полезная нагрузка |
| Запечатанные индексы (`.sbpt` / `.sbm`) | Вторичные индексы на диске |
| OpLog (активный хвост + архивные сегменты) | Упорядоченные изменения; без него свежие commit не восстановить |
| Конфиг узла | Профили, пиры, порты, `cluster-id` — restore должен совпасть с задуманной топологией |
| Каталог AUTH (`privileges.meta` под корнем каталога) | Пользователи и права — в ту же политику бэкапа, что и `dataDir` |

Типичная раскладка под корнем durability / репликации узла (имена из `SealedBaseBackupUtil`):

```text
<dataDir>/
  sealed/          # полезные нагрузки .gmap
  orchid/          # устойчивое состояние ORCHID
  locus/           # homologous locus
  index-ckpt/      # checkpoint индексов
  … сегменты OpLog + при необходимости отдельный oplog-archive
```

## API base-копии

Base для PITR на watermark `W` (офлайн / ops JVM, не Netty EL):

```text
SealedBaseBackupUtil.backupBase(dataDir, backupDir, W)
# установка в пустой dataDir:
SealedBaseBackupUtil.clearDataDir(dataDir)
SealedBaseBackupUtil.installBase(backupDir, dataDir)
```

Снимайте в тихом окне или после чистой остановки, чтобы sealed и orchid совпали. Восстановление до seq — [PITR](pitr.md) (`PitrRestoreMain`).

## Когда уплотнять (seal) и что это даёт

Уплотнение переносит накопившиеся записи из журнала в sealed-файлы и позволяет безопасно укорачивать OpLog (truncate) после watermark. Перед промышленной нагрузкой, которую может понадобиться откатить:

1. Включите архив журнала (`oplog-archive` / PITR) **заранее** — [PITR](pitr.md).
2. Снимайте base на известном watermark по расписанию или перед рискованными работами (миграция диска, смена major layout).
3. Не считайте успешной резервной копией один только снимок RAM или незапечатанный хвост.

## Практика резервного копирования

1. Лучше тихое окно или узел, который не единственный writer.
2. Копируйте `dataDir` согласованно: снимок файловой системы или холодная копия после чистой остановки. Не копируйте недописанные сегменты.
3. Храните копии вне машины; подписывайте `node-id`, время и версию бинарника.
4. Хотя бы раз отработайте restore на запасном хосте — до аварии.

## Порядок restore (холодный)

1. Остановите процесс Grid на этом узле.
2. Подмените `dataDir` резервной копией (sealed + OpLog + архив — как снимали).
3. Верните согласованный конфиг (пиры, порты, флаги durability, тот же `cluster-id`).
4. Запустите узел; дождитесь подгрузки и — если репликация включена — синхронизации ORCHID и подтягивания реплик.
5. Проверьте readiness Actuator до трафика ([мониторинг](../monitoring.md)).
6. Если узел должен стать writer — [повышение роли](ha-promote.md). Второго writer не поднимайте.

## После restore — матрица проверки

| Проверка | Критерий успеха |
|----------|-----------------|
| Процесс | Процесс узла жив; нет второго процесса на том же `dataDir` |
| Readiness | Actuator readiness UP; при репликации — `orchidSynced` / `orchid_r` выше допуска |
| Роль writer | Не больше одного `writerEligible: true` в кольце записи; повышение роли только если этот узел должен писать ([повышение роли](ha-promote.md)) |
| Путь приложения | Одна запись и одно чтение по реальному URL клиента (не HTTP `/replication/compare`) |
| Пиры | Реплики подтягиваются; не форсировать чтение при `applyLagStale` |
| Несколько площадок | Совпадение `regionEpoch` / ограждение Active, если PITR трогал Active |

Пока не прошли все применимые к топологии строки, restore не считают успешным.

## Несколько узлов

- Восстанавливайте **по одному** узлу. По возможности держите здорового writer, пока реплика подтягивается.
- После restore отстающие пиры догоняют журнал (SparseCatchUp / HomologousRepair) — [отказы](failures.md), [состояние репликации](../../understand/replication-state.md).
- Несколько площадок: учитывайте Active/Hold и `regionEpoch` — [несколько ЦОД](multi-dc.md). На Active действует ограждение PITR (`PitrActiveFence`).

## Типичные ошибки

| Симптом | Что проверить |
|---------|----------------|
| Узел стартует «пустым» при LAZY | Нормально: истина на sealed + хвосте OpLog; не путать с потерянным `dataDir` |
| Пиры не принимают узел | Чужой `cluster-id` / epoch; общий `dataDir` на два процесса |
| «Пропали» открытые TX после restore | Ожидаемо: грязный буфер до COMMIT в OpLog не пишется |
| Archive пуст, а нужен откат «на час назад» | Данных нет — архив включают **до** нагрузки |

## Чего не делать

- Не считать резервной копией только состояние в RAM.
- Не делить один `dataDir` на два процесса.
- Не «чинить» живой повреждённый каталог записью — сначала копия и PITR.
- Не пускать трафик до readiness UP.
