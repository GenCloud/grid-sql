# Безопасность и полномочия

Как устроены пользователи, AUTH на кадрах и GRANT в SQL. Это операторская страница: что включить до допуска приложений и чего продукт **не** делает сам.

Подробный синтаксис DDL: [DDL](../../sql/ddl.md). Порт и readiness: [SQL-сервер](../configuration/sql-server.md).

## Модель

| Слой | Роль |
|------|------|
| Кадр AUTH | Идентичность канала после connect (логин/пароль из URL) |
| Каталог `privileges.meta` | Пользователи, роли, GRANT на схемы/таблицы |
| ORCHID / OpLog | Допуск и сохранность **записи** — не AUTH |

AUTH **не** является 2PC и не решает, можно ли закоммитить строку. Сохранность — [долговременное хранение](../configuration/durability.md).

## Пустой каталог и первый администратор

| Состояние | Поведение |
|-----------|-----------|
| Пользователей нет | Вход без пароля; первый `CREATE USER` становится администратором |
| Пользователи есть | В URL нужны credentials; кадры без AUTH отклоняются |

Типичный bootstrap:

```sql
CREATE USER admin PASSWORD '…';
-- дальше только под admin
CREATE USER app PASSWORD '…';
GRANT SELECT, INSERT, UPDATE, DELETE ON SCHEMA public TO app;
```

Смена пароля: `ALTER USER … PASSWORD` (PBKDF2). Не храните пароли в общем конфиге репозитория.

## Что проверяется

- Привилегии на таблицы, включая стороны JOIN.
- Набор: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `DDL`.
- Роли: `CREATE ROLE` / `DROP ROLE` / `GRANT ROLE … TO user`.

Клиент (reactive `grid://` или JDBC `jdbc:grid://`) передаёт те же credentials в authority URL.

## Где хранится каталог

Файл `privileges.meta` лежит под каталогом SQL: `{grid.sql.data-dir}/catalog/privileges.meta` (по умолчанию рядом с `./data-…/catalog`). Это локальный файл узла, не общий NFS.

## Ограничения DDL

| Ожидание | Факт |
|----------|------|
| `REVOKE … FROM user` | Есть — снимает права у пользователя |
| `REVOKE ROLE` / снять членство роли с пользователя отдельной командой | Нет — членство снимается через `DROP ROLE` |
| Права на роль (`GRANT … TO ROLE`) | Есть; проверка идёт через членство пользователя |

## Чего нет в продукте

| Ожидание | Факт |
|----------|------|
| TLS / mTLS на SQL-порту из коробки | Нет — при необходимости терминация TLS снаружи (прокси/LB) |
| Отдельный IdP / OAuth | Нет — локальный каталог пользователей |
| Row-level security | Нет |
| AUTH как арбитр коммита | Нет |

## Сеть и TLS до bootstrap

| Шаг | Действие |
|-----|----------|
| 1 | SQL-порт (**15432**) открыт только доверенным сетям / LB; репликация (**5615**) — отдельный контур между узлами |
| 2 | Пока каталог пуст — любой, кто дотянулся до порта, может создать admin: ограничьте доступ до первого `CREATE USER` |
| 3 | TLS на SQL-порту в продукте нет — при необходимости терминация на прокси/LB перед узлом |
| 4 | После первого пользователя приложения получают credentials в URL (`grid://` / `jdbc:grid://`) |

Чеклист оператора: firewall → первый admin → `GRANT` приложению → readiness UP → трафик.

## Ротация credentials

После включения AUTH (в каталоге уже есть пользователи) меняйте пароль через `ALTER USER … PASSWORD`, затем обновите URL / секреты приложений. Не оставляйте passwordless bootstrap: после первого admin кадры без AUTH отклоняются. Файл `privileges.meta` храните на локальном диске узла и включайте в ту же политику бэкапа, что и `dataDir` узла — не на общий NFS.

**Периодичность.** Интервал — по политике секретов (смена людей, фиксированное расписание). Сначала admin в окне обслуживания, затем пользователи приложений; старый пароль держите только пока все клиенты не получили новый секрет в URL. Проверка: вход с новым паролем успешен; со старым — отказ.

### Revoke и минимальные права

```sql
-- сузить приложение, которому нужно только чтение
REVOKE INSERT, UPDATE, DELETE ON SCHEMA public FROM app;
GRANT SELECT ON SCHEMA public TO app;
```

После `REVOKE` открытые сессии могут ещё держать старые права до reconnect — перезапустите или переподключите клиентов.

### TLS снаружи узла

В продукте нет TLS на SQL-порту. Поставьте reverse proxy или балансировщик, который терминирует TLS и пробрасывает plaintext только в частной сети на **15432**. Репликация (**5615**) — отдельный контур между узлами; не публикуйте её в интернет.

## Эксплуатационные правила

1. До появления пользователей любой, кто дотянулся до порта, может создать admin — ограничьте сеть.
2. После первого пользователя без credentials в URL приложения не зайдут.
3. Не путайте порт SQL (**15432**) с репликацией (**5615**).
4. Readiness UP не заменяет AUTH: канал может быть готов, а кадр без логина — отклонён.
