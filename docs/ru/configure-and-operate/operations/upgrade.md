# Обновление и перезапуск узла

Как сменить бинарник или перезапустить узел, не потеряв `dataDir` и не получив двух писателей. Короткий регламент; детали HA и Multi-DC — на связанных страницах.

## Перед обновлением

1. Убедиться, что `dataDir` локальный на узел (не NFS/SAN на кластер).
2. При durability: `fsync: true`; при необходимости свежий **base** PITR на watermark ([PITR](pitr.md)).
3. Зафиксировать, кто сейчас writer (`writerEligible` / мета клиента).
4. Приложение готово к `PROMOTE_NOTIFY` / `rediscoverWriter()` — [повышение роли](ha-promote.md).
5. Записать версии jar/образа «до» и целевую «после» (для отката бинарника).

## Поэтапный перезапуск (кольцо с репликацией)

Порядок: сначала **не-writer** (реплики), в конце — текущий писатель (или сначала передать роль, затем обновить бывший writer).

На каждом узле:

1. Слить трафик / дождаться отсутствия своих записей на этом процессе.
2. Корректный stop (SIGTERM / Spring shutdown) — force mmap и атомарный `.wpos`.
3. Подменить jar / образ; **тот же** `dataDir` и конфиг шардов / `cluster-id`.
4. Старт; дождаться readiness UP и ORCHID sync.
5. Проверить подтягивание (`applyLag`), затем следующий узел.

### Кольцо со смешанными версиями

Во время поэтапного обновления в кольце кратко могут жить **две версии бинарника**. Это ожидаемо при поэтапном перезапуске на совместимом формате каталога данных. Не оставляйте смешанное кольцо постоянно: доведите все узлы, затем проверьте.

| Сочетание | Кратко допустимо? | Заметки |
|-----------|-------------------|---------|
| Один major формат sealed/OpLog, две версии jar | Да, только на время поэтапного обновления | Доведите все узлы; затем одна версия |
| `.sbpt` VERSION 2 на одних узлах, VERSION 1 на других | Нет как постоянное состояние | VERSION 1 при чтении отклоняется. До обновления — base PITR; после — reseal / `dumpDomain` на каждом узле, затем одна версия |
| Несовместимый формат `dataDir` между узлами | Нет | Сначала PITR base; мигрируйте одно семейство формата за раз |
| Два процесса / два бинарника на одном `dataDir` | Никогда | Инцидент — остановить лишний процесс |

После возврата каждого узла:

1. Actuator readiness UP; при репликации — ORCHID sync (`orchidSynced` / `orchid_r` выше допуска).
2. На целевом writer: `writerEligible: true` и совпадение меты клиента (`PROMOTE_NOTIFY` / AUTH) — [повышение роли](ha-promote.md).
3. Реплики: `applyLagStale` false (или в пределах принятой политики отставания) до чтения с них.
4. Одна проверочная запись и чтение по пути приложения (не HTTP `/replication/compare` как источник writer).

`SIGKILL` хуки не вызывает — следующий open идёт через replay порванного хвоста OpLog; это штатно, но дольше.

## Один узел (solo durable)

1. Остановить процесс.
2. Сменить бинарник; сохранить `dataDir`.
3. Старт; при `hydrate-mode: LAZY` «пустая» RAM нормальна — истина на sealed + хвосте OpLog.

## Эпоха схемы, раскладка и клиенты

- Смена схемы (DDL) фиксируется в каталоге; клиенты с устаревшей метаданной сессией переподключаются.
- Duplex / codec `schema-epoch` в YAML не путать с ORCHID seq — см. [Duplex](../../performance/perf-duplex.md). Не поднимайте epoch «на всякий случай» на живом `dataDir`, который пиры ещё читают со старой эпохой.
- После смены writer клиент **не** крутит следующий host в URL вручную.
- Смена major формата `dataDir` (несовместимый sealed/OpLog) — сначала base + проверка archive, затем миграция по процедуре поставщика бинарника. В одном кластере держите одно семейство формата, пока все узлы не обновлены.
- Не меняйте `cluster-id`, число шардов существующих таблиц и не делитесь одним `dataDir` между двумя бинарниками во время обновления.

## Откат бинарника

| Ситуация | Действие |
|----------|----------|
| Новый бинарник не стартует / readiness DOWN | Вернуть предыдущий jar/образ на **том же** `dataDir`; не создавать второй процесс |
| Данные повреждены после неудачного старта | Не «дописывать» — [PITR](pitr.md) на копии, затем вернуть узел |
| Нужен откат состояния «как час назад» | Только PITR до `--until-seq`, не откат jar |

## Когда нужен PITR base до обновления

| Ситуация | Base |
|----------|------|
| Обычный поэтапный перезапуск на том же major формате данных | Желателен по расписанию, не обязателен на каждый рестарт |
| Миграция `dataDir`, сомнение в диске, смена хоста | Снять base + проверить archive **до** работ |
| Откат «как было час назад» | Только PITR до `--until-seq` |

## Чего не делать

- Два процесса на одном `dataDir`.
- Обновлять все узлы сразу без подтягивания.
- Отключать репликацию / fsync «на время обновления» без явного окна потерь.

**Связанное:** [отказы](failures.md), [PITR](pitr.md), [долговременное хранение](../configuration/durability.md), [Compose](deploy-compose.md).

## Типовые сбои при обновлении

| Симптом | Действие |
|---------|----------|
| Readiness DOWN после старта с репликацией | Ждать ORCHID sync; смотреть `orchid_r` / peers — не слать трафик |
| Клиент пишет на старый host | `rediscoverWriter()` / `PROMOTE_NOTIFY`, не следующий host в URL |
| Долгий старт после `SIGKILL` | Replay порванного хвоста OpLog — ожидаемо; следующий stop — SIGTERM |
| `applyLagStale` на первой реплике после обновления | Дождаться подтягивания перед чтением с неё |
| Два процесса на одном `dataDir` | Немедленно остановить лишний; это не «обновление», а инцидент ([отказы](failures.md)) |

После полного поэтапного обновления: все узлы на целевой версии; один writer; проверочная запись и чтение по пути приложения.

### Проверка после обновления

| Проверка | Ожидание |
|----------|----------|
| Actuator readiness UP на каждом узле | SQL слушает; при репликации — ORCHID sync |
| Ровно один `writerEligible: true` | Мета клиента совпадает (`PROMOTE_NOTIFY` / AUTH) |
| Одна запись и чтение по пути приложения | Не `/replication/compare` как источник writer |
| Реплики до чтения | `applyLagStale` false (или в пределах политики) |
| Пользователи / AUTH (если включены) | `privileges.meta` на **каждом** SQL-узле, куда ходят приложения |
