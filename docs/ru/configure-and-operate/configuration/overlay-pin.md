# Закрепление ключей в overlay

`PIN KEY` замораживает размещение шарда, в котором лежит ключ: пока пометка жива, адаптивное размещение не передаёт этот шард другому узлу. Это только про размещение — ключ не кэшируется сильнее обычного и не блокируется.

## Когда размещение нужно заморозить

При включённой репликации `AdaptiveReplicaSwarm` оценивает узлы на скользящем окне (нагрузка, RTT, heap, цена подтягивания отстающей реплики) и может переносить владение шардами. В среднем это балансирует кластер. Для небольшого набора ключей это вредно:

- Горячий ключ или сервис с основной долей запросов к шарду: после переноса владения реплика резко догоняет журнал, задержки растут.
- Долгая интерактивная сессия, которой нужна стабильная локальность ключа.
- Редко записываемые ключи конфигурации на шарде, который постоянно переезжает из-за горячих соседей.
- Окно разбора инцидента, когда владение не должно меняться, пока собираются логи и метрики.

Без явного управления перебалансировка идёт только по метрикам. Закрепление выражает намерение оператора или приложения: не переносить этот шард, пока существует аннотация.

## Включение

```yaml
grid:
  overlay:
    enabled: true            # необходимо для PIN / UNPIN
    durable: true            # аннотации переживают перезапуск
    auto-pin-ttl-ms: 0       # в production оставляйте 0
```

| Параметр | По умолчанию | Действие |
|----------|--------------|----------|
| `grid.overlay.enabled` | `false` | Без него `PIN KEY` отвергается с `overlay is disabled (grid.overlay.enabled=false)` |
| `grid.overlay.durable` | `false` | Сохраняет аннотации в `{dataDir}/{cluster}/{node}/overlay/`, чтобы они переживали перезапуск |
| `grid.overlay.auto-pin-ttl-ms` | `0` | Больше нуля — путь записи обновляет короткое закрепление на каждой горячей записи |

Закрепление действует только там, где размещение иначе выполнило бы перенос. На одиночном узле без пиров `PIN KEY` принимается и записывается, но ничего не меняет.

## Операторы

```sql
PIN KEY <таблица> <литерал-ключа> [TTL <мс>] [QOS <метка>];
UNPIN KEY <таблица> <литерал-ключа>;
```

```sql
PIN KEY orders 9001 TTL 3600000 QOS 'vip-tenant';
PIN KEY sessions 'sess-abc' TTL 1800000;
PIN KEY config 'root';             -- без срока: до явного UNPIN
UNPIN KEY orders 9001;
```

`TTL` задаётся в миллисекундах. Закрепление без `TTL` действует до явного `UNPIN`. Повторный `PIN` того же ключа продлевает окно. Когда последнее закрепление на шарде снято или истекло, перенос снова возможен на следующем такте размещения.

## Область действия

| Слой | Эффект |
|------|--------|
| Хранилище overlay | Аннотация по имени таблицы и хешу ключа, с необязательным сроком и меткой качества обслуживания |
| Размещение | Подавление переноса действует на **шард** (`isOverlayBlockingShardMigrate`), вычисленный из ключа. Остальные шарды продолжают переезжать |
| Сохранность | При `durable: true` аннотация переживает перезапуск |
| Метрика | `grid.replication.overlay_pinned_keys` |

| Слой | На что не влияет |
|------|------------------|
| Байты строки, журнал, согласие | Закрепление — аннотация, а не изменение данных |
| Планы запросов | Закрепления плана нет |
| Рабочий набор и чтение запечатанных файлов | Строка по-прежнему вытесняется и подгружается при промахе |
| Атомарность транзакций и блокировки записей | Не связано; используйте транзакции и блокировки |
| Другие шарды | Закрепление ключа A не замораживает шард с ключом B |

`hasAnyPinned()` и `isOverlayBlockingSwarmMigrate()` — общекластерные показатели: они сообщают, что существует хотя бы одно закрепление. Решение о переносе принимается только по проверке конкретного шарда. Интеграционное покрытие: `index.unit.overlay.OverlayPinSqlIT`.

## Процедуры

### Заморозить горячего клиента на время пика

1. Определите шард под давлением по событиям размещения или по частоте запросов клиента.
2. Закрепите ключ клиента на окно, равное пику:

```sql
PIN KEY orders 9001 TTL 3600000 QOS 'vip-tenant';
```

3. Убедитесь, что `grid.replication.overlay_pinned_keys` выросла, и что такты размещения больше не применяют переносы владения для этого шарда.
4. Снимите закрепление после пика или дайте истечь сроку:

```sql
UNPIN KEY orders 9001;
```

Задавайте срок близко к ожидаемой длительности пика. Забытое закрепление без `TTL` навсегда лишает этот шард перебалансировки. Если пик затянулся, повторите оператор.

### Заморозить размещение на время разбора

1. Перечислите шарды, затронутые инцидентом, и выберите по одному представительному первичному ключу на шард — подавление работает по шардам, одно закрепление не покрывает всю таблицу.
2. Закрепите их на окно обслуживания:

```sql
PIN KEY orders 9001 TTL 900000 QOS 'ops-freeze';
PIN KEY config 'root' TTL 900000 QOS 'ops-freeze';
```

3. Завершите диагностику или выведите узел из ротации по [регламенту отказов](../operations/failures.md).
4. Снимите метки заморозки и убедитесь, что показатель числа закреплений вернулся к базовому значению.

### Сохранить локальность сессии

Для таблицы с ключом по сессии приложение закрепляет ключ при старте сессии и снимает при завершении:

```sql
PIN KEY sessions 'sess-abc' TTL 1800000 QOS 'session';
-- работа сессии
UNPIN KEY sessions 'sess-abc';
```

Задавайте срок как максимальное время простоя сессии плюс расхождение часов, чтобы упавшее приложение не оставило шард замороженным. Закрепление не заменяет транзакцию и не изолирует писателя — строка сессии подчиняется обычным правилам транзакций.

### Стабилизировать шард конфигурации

Небольшая, редко записываемая таблица конфигурации может лежать на шарде, который размещение постоянно переносит из-за шумных соседей. Каждый перенос — чистые накладные расходы для её читателей:

```sql
PIN KEY config 'root' QOS 'config';
```

Снимайте закрепление только при переносе домена или выводе узла из эксплуатации. Ставьте `durable: true`, чтобы закрепление пережило поэтапный перезапуск.

### Автоматическое закрепление на горячих записях

`auto-pin-ttl-ms` больше нуля заставляет путь записи обновлять короткое закрепление для недавно записанных ключей, без операторов из приложения:

```yaml
grid:
  overlay:
    enabled: true
    durable: false
    auto-pin-ttl-ms: 60000
```

Это уместно только при равномерно горячем распределении ключей. При массовой загрузке широкий набор записей затрагивает много шардов, и, поскольку подавление работает по шардам, кластер может оказаться замороженным почти целиком. В production держите `auto-pin-ttl-ms: 0` и закрепляйте известные ключи явно, пока длительный нагрузочный прогон не покажет обратного.

## Проверка

1. Прочитайте `grid.replication.overlay_pinned_keys` до и после оператора.
2. Убедитесь, что `ReplicationCoordinator.isOverlayBlockingShardMigrate(table, shard)` возвращает `true` для шарда закреплённого ключа и `false` для несвязанного шарда.
3. Смотрите логи размещения: закреплённый шард пропускается, тогда как остальные могут переключаться, поскольку `swarm.apply-auto-cutover` по умолчанию `true`.
4. При `durable: true` перезапустите узел и убедитесь, что закрепление на месте и всё ещё блокирует перенос.

## Антипаттерны

| Практика | Почему не работает |
|----------|--------------------|
| Считать закрепление аналогом закрепления буфера или плана | Оно не влияет ни на память, ни на оптимизатор |
| Закреплять каждую строку, затронутую транзакцией | Лишний оборот аннотаций и возможная заморозка множества шардов |
| Полагаться на закрепление ради сохранности или согласованности | Их дают согласие, журнал, запечатанные файлы и транзакции |
| Оставлять бессрочные закрепления без ревизии | Эти шарды перестают перебалансироваться навсегда |
| Большой `auto-pin-ttl-ms` при массовой загрузке | Постоянные закрепления заморозят все затронутые шарды |
| Ожидать, что одно закрепление заморозит всю таблицу | Подавление намеренно ограничено шардом с этим ключом |
