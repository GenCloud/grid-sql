# Репликация

Репликация отправляет закоммиченные записи журнала на другие узлы, допускает запись только при кворуме согласия (*ORCHID*) и закрывает пропуски во время подтягивания. Это отдельный слой от локального хранения: пиры включаются ключом `grid.replication.enabled`, тогда как [долговременное хранение](durability.md) работает и вовсе без пиров.

Транспорт между узлами — всегда Netty на собственном порту. Каждый узел держит свой каталог данных.

## Минимальная отказоустойчивая пара

| Узел | Профиль | Порт SQL | Порт репликации |
|------|---------|---------:|----------------:|
| primary-1 | `primary` | 15432 | 5615 |
| replica-1 | `replica` | 15433 | 5616 |

```yaml
grid:
  replication:
    enabled: true
    node-id: primary-1
    cluster-id: example-grid
    orchid:
      order-threshold: 0.85
      digest-quorum: MAJORITY
    transport:
      bind-host: 127.0.0.1
      bind-port: 5615
      peers:
        - { id: replica-1, host: 127.0.0.1, port: 5616, dc: dc-a }
    ha:
      max-stale-lag: 10000
      replica-reads-enabled: true
    op-log:
      fsync: true
```

Замените `bind-host: 127.0.0.1` на интерфейс, доступный пирам: привязка к loopback работает только когда оба узла работают на одном хосте.

## Параметры, которые обязаны быть верны до первой записи

| Параметр | По умолчанию | Что будет при ошибке |
|----------|--------------|----------------------|
| `enabled` | `false` | Пиры не запускаются, узел работает в одиночку |
| `node-id` | `node-1` | Совпадающие идентификаторы ломают HELLO и подсчёт кворума |
| `cluster-id` | `grid-default` | Пир с другим идентификатором кластера отвергается |
| `transport.bind-host` / `bind-port` | `0.0.0.0` / `5615` | Нет входящего канала от пиров |
| `transport.peers` | `[]` | При ожидаемом размере больше одного узел не собирает кворум, готовность остаётся DOWN |
| `orchid.order-threshold` | `0.85` | Допуск записи становится либо слишком мягким, либо заблокированным навсегда |
| `orchid.digest-quorum` | `MAJORITY` | Кворум считается по настроенным голосующим узлам того же сайта |
| `op-log.fsync` | `true` | Подтверждённые коммиты могут исчезнуть после аварии хоста |

Одиночная запись разрешена только при первичном запуске с пустым списком пиров. После разрыва сети узел не переходит в одиночный режим, а `forgetPeer` не уменьшает настроенный кворум — это не способ продолжать писать половиной кластера.

## Тонкая настройка согласия и транспорта

| Параметр | По умолчанию | Замечания |
|----------|--------------|-----------|
| `orchid.coupling` | `15.0` | Сила связи фаз; менять только по результатам измерений |
| `orchid.natural-freq-hz` | `1.0` | Держите `2·π·freq·tick/1000` заметно меньше `1` |
| `orchid.tick-ms` | `10` | Период такта синхронизации; меньшие значения дороже по CPU |
| `orchid.max-propose-in-flight` | `64` | Число одновременных предложений; повышать только если узкое место — допуск, а не диск |
| `transport.connect-timeout-ms` | `5000` | Таймаут подключения к пиру |
| `transport.max-frame-bytes` | `16777216` | Потолок кадра репликации, 16 МиБ |
| `flow.max-inflight-ops` | `10000` | Порог обратного давления при отправке; смотрите `grid.replication.ship_backpressure` |
| `repair.homologous-enabled` | `true` | Фоновое закрытие пропусков |
| `repair.reconcile-interval-ms` | `5000` | Период сверки |
| `ha.max-stale-lag` | `10000` | Потолок отставания применения (число операций журнала) для чтений с реплики; `Long.MAX_VALUE` отключает порог |
| `ha.replica-reads-enabled` | `false` | В библиотеке выключено; профили сборки `primary` и `replica` включают |

Размещение шардов (`swarm.*`, `placement-optimizer.*`) включено по умолчанию и само переносит владение шардами; `swarm.apply-auto-cutover` по умолчанию `true`. Если размещение нужно зафиксировать на время разбора инцидента или на пик, используйте [закрепление в overlay](overlay-pin.md), а не отключение подсистемы.

## Порядок ввода в строй

1. Задайте каждому узлу уникальный `node-id` и общий `cluster-id`.
2. Направьте `transport.peers` каждого узла на порты репликации остальных узлов — никогда на их порты SQL.
3. Запустите узлы и дождитесь готовности. При включённой репликации готовность остаётся DOWN до синхронизации согласия; это ожидаемо и не означает неработающий порт SQL.
4. Убедитесь, что в деталях готовности `orchidSynced: true` и `orchidR` выше `order-threshold`.
5. Убедитесь, что ровно один узел сообщает `writerEligible: true`.
6. Выполните одну запись и одно чтение по пути приложения, затем проверьте отставание применения на репликах.

Клиент не выбирает писателя по конфигурации: он берёт его из метаданных протокола (`ServerMeta`, `PROMOTE_NOTIFY`) — см. [передачу роли писателя](../operations/ha-promote.md).

## Режимы между сайтами

`grid.replication.cross-dc.mode` задаёт путь записи между сайтами:

- `ASYNC_SHIP` — коммит завершается локально, журнал уходит асинхронно. Цена — окно возможных потерь на резервном сайте.
- `SYNC_VOTERS_ACROSS_DC` — коммит ждёт подтверждения дайджеста с удалённой стороны. Цена — обход глобальной сети на каждой записи.

Ограждение сайтов (`grid.replication.region.enabled`, по умолчанию `false`) разделяет роли Active, Hold и Witness и защищает от двух писателей. Подробнее: [несколько сайтов](../operations/multi-dc.md), [несколько сайтов под нагрузкой](../operations/cluster-multidc-highload.md).

## Симптом и действие

| Симптом | Причина | Действие |
|---------|---------|----------|
| Готовность DOWN с `reason: orchid_not_synced` | Пиры недоступны или порядок фаз ниже порога | Проверить связность пиров и `grid.replication.connect_failures`; нагрузку пока не подавать |
| Запись отвергается с ошибкой несинхронности | Кворум недоступен | Восстановить связность или диск; не понижать `fsync` и порог ради проталкивания трафика |
| `enabled: true` при пустом списке пиров на многоузловом кластере | Ошибка конфигурации | Заполнить `transport.peers`; не сокращать кворум через `forgetPeer` |
| `bad frameLen` на клиентском соединении | Клиент направлен на порт репликации | Использовать порт SQL (по умолчанию 15432) |
| HELLO не сходится | Разный `cluster-id`, дублирующийся `node-id` или порт SQL в `peers` | Исправить идентификаторы и порты |
| Повреждённый журнал на двух узлах | Два процесса используют один каталог данных | По одному каталогу на процесс, на локальном диске |
| `repair_issued` растёт, `repair_applied` нет | Диск или сеть пира, расхождение номеров последовательности | Смотреть логи восстановления и номера на пирах — [состояние репликации](../../understand/replication-state.md) |

## Ограничения

- Один каталог данных на узел. Общие пути NFS или SAN повреждают журнал и запечатанные файлы.
- Пробы оркестратора — Actuator `/health/liveness` и `/health/readiness`. HTTP-сверка отставания — лабораторное средство, а не поиск писателя.
- Заявленное поведение хранения предполагает `op-log.fsync: true` на каждом узле, который может стать писателем.
