# Долговременное хранение

Узел хранит данные на диске через журнал изменений (*OpLog*) и запечатанные файлы карты (*sealed* `.gmap`, `.sbpt`, `.sbm`). Этот путь не требует соседних узлов: `grid.durability.enabled` не зависит от `grid.replication.enabled`, и одиночный узел с пустым списком пиров полностью сохраняет данные.

При включённом хранении коммит сначала дописывается в журнал и подтверждается, и только потом строка становится видимой в карте в памяти. Если запись в журнал не удалась, коммит отменяется целиком, без частичного применения. В памяти держится рабочий набор, а не единственная копия данных.

Отправка на другие узлы, кворум и подтягивание — отдельный слой, см. [репликацию](replication.md).

## Эталонный профиль

```yaml
grid:
  durability:
    enabled: true
    hydrate-mode: LAZY          # FULL | LAZY
    working-set-max-entries: 262144
    adaptive-disk-first: true
    oplog-archive:
      enabled: false            # обязателен для PITR
      dir: ./data/oplog-archive
  replication:
    op-log:
      data-dir: ./data-primary/replication
      fsync: true
      segment-size: 64
```

Параметры журнала лежат в `grid.replication.op-log.*` даже при выключенной репликации: OpLog общий для локального пути хранения и для отправки на пиры.

Профили сборки `primary`, `replica` и `capacity` уже выставляют `fsync: true`, `hydrate-mode: LAZY` и ограниченный рабочий набор.

## Параметры

| Параметр | По умолчанию | Действие |
|----------|--------------|----------|
| `grid.durability.enabled` | `true` | Коммит проходит через согласие (*ORCHID*) и журнал до появления в памяти; сбой журнала отменяет коммит |
| `grid.durability.hydrate-mode` | `FULL` | `FULL` — загрузить запечатанные файлы и журнал в память на старте; `LAZY` — отобразить запечатанные файлы (*mmap*) и проиграть только хвост журнала |
| `grid.durability.working-set-max-entries` | `0` (без ограничения) | Потолок рабочего набора. Выше `0` холодные закоммиченные ключи вытесняются по LRU; грязные и ещё не слитые из очереди записи не вытесняются никогда |
| `grid.durability.adaptive-disk-first` | `true` | При давлении на диск сильнее опираться на подгрузку с запечатанных файлов, а не растить память |
| `grid.durability.oplog-archive.enabled` | `false` | Перед обрезкой копировать диапазон журнала в архив; ошибка копирования отменяет обрезку |
| `grid.durability.oplog-archive.dir` | `./data/oplog-archive` | Корень архива, его читает [PITR](../operations/pitr.md) |
| `grid.durability.oplog-archive.stream-enabled` | `false` | Поток журнала за пределы узла, только дозапись, при безопасной обрезке |
| `grid.durability.oplog-archive.stream-dir` | `""` | Корень потока; пустое значение разворачивается в `{dir}/stream` |
| `grid.replication.op-log.data-dir` | `./data/replication` | Каталог сегментов журнала, отдельный для каждого узла |
| `grid.replication.op-log.fsync` | `true` | `FileChannel.force` при дозаписи. `false` допустим только для поиска узкого места на тестовом хосте |
| `grid.replication.op-log.segment-size` | `1024` | Размер сегмента в МиБ; задаёт ротацию и шаг обрезки |

По умолчанию `hydrate-mode` равен `FULL`, и для большинства production-корпусов это неверный выбор. Указывайте `LAZY` явно, если запечатанный набор не укладывается в heap с запасом.

## Выбор режима прогрева

| Режим | Старт | Память после старта | Промах по ключу |
|-------|-------|---------------------|-----------------|
| `FULL` | Дольше: запечатанные файлы и журнал читаются в память | Рабочий набор сразу тёплый | Редко — ключи уже в памяти |
| `LAZY` | Быстрее: запечатанные файлы отображаются, проигрывается только хвост журнала | Растёт по мере обращений | Подгрузка с запечатанного файла |

`FULL` выбирают, когда запечатанный корпус небольшой и первые запросы после перезапуска не должны платить за обращение к диску. `LAZY` выбирают, когда корпус велик относительно heap или когда долгий старт хуже периода прогрева — это обычная production-настройка.

## Подбор размера рабочего набора

1. Начните с `working-set-max-entries` примерно равного числу строк, которые горячие запросы затрагивают за час пика.
2. Следите за счётчиками промахов запечатанного слоя (`grid.sealed.miss`, `grid.replication.sealed_misses`) и за `grid.replication.map_hit_rate` — см. [мониторинг](../monitoring.md).
3. Если доля промахов остаётся высокой, а в heap есть запас, поднимайте потолок. Если растут давление на heap и паузы сборщика мусора, снижайте и оставляйте `adaptive-disk-first: true`.
4. Оставляйте `0` только тогда, когда весь корпус должен постоянно находиться в памяти и heap рассчитан на это.

Вытеснение никогда не касается незавершённой работы: грязные буферы транзакций и записи в очереди записи остаются в памяти до коммита.

## Артефакты на диске

| Артефакт | Роль |
|----------|------|
| Сегменты OpLog | Журнал изменений; обрезается только до отметки запечатывания |
| Запечатанные `.gmap` | Полезная нагрузка строк на диске |
| `.sbpt` / `.sbm` | Запечатанные вторичные и bitmap-индексы |
| orchid `state.bin` | Последний подтверждённый номер последовательности |
| `locus/` | Состояние восстановления `HomologousRepair` |
| `index-ckpt/` | Каталог контрольных точек индексов |
| `oplog-archive/` | Необязательный архив для восстановления на выбранный номер последовательности |

Как устроены чтение и отображение файлов: [хранение GMAP](../../understand/storage-sealed-gmap.md).

## Запечатывание, обрезка, архив

1. Коммиты копятся в журнале, при `fsync: true` каждая дозапись сопровождается `force`.
2. Запечатывание уплотняет хвост журнала в файлы `.gmap` и `.sbpt` и поднимает отметку.
3. Обрезка режет журнал только до этой отметки. При `oplog-archive.enabled: true` диапазон сначала копируется в архив; ошибка ввода-вывода отменяет обрезку, а не теряет диапазон.
4. После перезапуска источник истины — запечатанные файлы плюс хвост журнала, а для восстановления на точку во времени ещё и архив.

Одиночный узел (`grid.replication.enabled: false`) проходит тот же порядок без пиров.

## Проверка сохранности после перезапуска

Выполните это на стенде, прежде чем полагаться на конфигурацию:

1. Вставьте заведомо известную строку и закоммитьте; запомните первичный ключ.
2. Убейте процесс без штатного завершения (`SIGKILL` / `Stop-Process -Force`). Так вы получите порванный хвост журнала — именно этот случай нужно проверить.
3. Запустите узел на том же `dataDir`. Сервер обрежет порванный хвост и проиграет целые записи.
4. Прочитайте строку по первичному ключу. Она должна найтись.
5. Выполните `SELECT` по неключевой колонке той же таблицы. Discovery гидратирует шарды, а хвост журнала индексируется пакетом изменений, поэтому вторичный поиск тоже обязан вернуть строку (проверяется тестом `LazySelectAfterRestartTest`).
6. Убедитесь, что готовность в Actuator равна UP, и только затем подавайте трафик приложения — [мониторинг](../monitoring.md).

При `LAZY` низкое потребление памяти сразу после шага 3 ожидаемо и не означает потерю данных.

## Симптом и действие

| Симптом | Причина | Действие |
|---------|---------|----------|
| После аварии не хватает свежих коммитов | `fsync: false` | Поставить `grid.replication.op-log.fsync: true`; цифры пропускной способности без fsync не использовать |
| Повреждённые сегменты журнала или запечатанные файлы на двух узлах | Общий `dataDir` на NFS/SAN | По одному локальному каталогу на узел; не разделять каталог данных между процессами |
| Долгий старт или нехватка памяти при запуске | `hydrate-mode: FULL` на большом запечатанном корпусе | Перейти на `LAZY` и ограничить `working-set-max-entries` |
| Холодные ключи медленнее обычного после перезапуска | Штатное поведение `LAZY` | Ничего; ключи подгрузятся при промахе и останутся в рабочем наборе |
| `SELECT` по неключевой колонке пуст, а по первичному ключу работает | Устаревшая сборка без гидратации при discovery | Обновиться; проверить процедурой выше |
| После потери данных восстанавливать нечего | `oplog-archive` был выключен | Включать архив заранее — [PITR](../operations/pitr.md) |
| Обрезка не идёт, журнал растёт | Каталог архива недоступен для записи или заполнен | Починить ввод-вывод архива; заблокированная обрезка — это намеренная защита |

## Ограничения

- `dataDir` и `op-log.data-dir` — на узел. Один общий каталог на кластер не поддерживается.
- Архив PITR включают до инцидента; задним числом его не собрать.
- При включённом хранении память — рабочий набор. Планировать её как единственную копию данных нельзя.
