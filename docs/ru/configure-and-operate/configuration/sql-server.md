# Сервер SQL

`SqlServerRuntime` владеет каталогом SQL, движком и — если включён приём SQL по TCP — конечной точкой Netty `SqlServer`. Приложения его не встраивают: они подключаются через `grid-sql-client`, либо реактивно по `grid://`, либо через JDBC по `jdbc:grid://`. Оба интерфейса используют один и тот же кадровый протокол на одном порту.

Серверная сторона: какие ключи включают слушатель, как убедиться, что он принимает трафик, и какие отказы приходят от сервера, а не от сети.

## Включение слушателя

`grid.sql-server.enabled` по умолчанию `false`, поэтому простое встраивание библиотеки не открывает порт. Профили сборки `primary`, `replica` и `capacity` включают его. Клиентские приложения этот ключ не задают.

```yaml
grid:
  sql-server:
    enabled: true
    host: 0.0.0.0
    port: 15432
  sql:
    default-shards: 8
    data-dir: ./data-primary/catalog
    lock-wait-timeout-ms: 8000
    prepare-pool-size: 64
```

| Ключ | По умолчанию | Значение |
|------|--------------|----------|
| `grid.sql-server.enabled` | `false` | Поднять слушатель SQL TCP |
| `grid.sql-server.host` | `0.0.0.0` | Адрес привязки; ограничьте его на многоинтерфейсном хосте |
| `grid.sql-server.port` | `15432` | Порт SQL |
| `grid.sql-server.user` / `password` | `grid` / `grid` | Начальный администратор при пустом каталоге (полные права). Оба пустые → вход без пароля до первого `CREATE USER` |
| `grid.sql.default-shards` | `4` | Число шардов для таблиц, созданных без явного указания |
| `grid.sql.data-dir` | `./data/catalog` | Корень каталога; внутри лежит `catalog/privileges.meta` (на узел; репликация не доставляет) |
| `grid.sql.lock-wait-timeout-ms` | `8000` | Предел ожидания блокировки записи до ошибки `lock wait timeout` |
| `grid.sql.prepare-pool-size` | `64` | Пул подготовленных запросов на движок |
| `grid.sql.catalog-meta-cache-size` | `256` | Размер кэша метаданных каталога |
| `grid.sql.timezone` | `UTC` | Часовой пояс сессии по умолчанию |
| `grid.sql.recursive-cte-max-depth` | `32` | Предел глубины рекурсивных обобщённых табличных выражений |

Блокировки `FOR UPDATE` на пирах (при включённой репликации) строятся из **`peers` репликации**, а не из `grid.sql.distributed-peers` — см. [чтение с реплики](../operations/replica-reads.md).

`grid.sql.distributed-peers` — другой параметр: включает **разлёт только чтения SELECT/JOIN** на удалённые SQL-пиры (`DistributedKeyFanOut` в исполнителе запросов). Пустой список = только локальные запросы. Агенты блокировок Dist FOR UPDATE этим ключом **не** ставятся.

Выбирайте `default-shards` по самым крупным ожидаемым таблицам: параметр задаёт параллелизм по шардам и не меняется у существующей таблицы без её пересоздания. От восьми до шестнадцати шардов — разумный стартовый диапазон на многоядерном хосте.

## Раскладка портов

| Порт | Протокол | Клиенты |
|-----:|----------|---------|
| 15432 | Кадры SQL (`grid://`, `jdbc:grid://`) | Приложения, DBeaver, средства нагрузки |
| 5615 и далее | Netty репликации | Только узлы |
| 7777 (primary по умолчанию в starter) | HTTP Actuator | Пробы оркестратора, сбор метрик |
| 7778 (профили `replica` и `capacity`) | HTTP Actuator | То же на процессе реплики или capacity |

Клиент SQL, направленный на порт репликации, падает на разборе кадра с ошибкой `bad frameLen`. Если на одном хосте работают несколько узлов, дайте каждому свой порт SQL, свой порт репликации и свой `server.port` для Actuator.

## Типовые профили

| Профиль | Порт SQL | Роль |
|---------|---------:|------|
| `primary` | 15432 | Писатель локальной пары |
| `replica` | 15433 | Реплика этой пары |
| `capacity` | 15432 | Одиночный узел с хранением, без репликации |

## Одновременные сессии в одном соединении

Одно соединение TCP несёт множество логических сессий. Клиент открывает сессию на каждый `TxContext`; сервер ограничивает число одновременно открытых сессий в одном канале и отвечает `maxTxContexts=N exhausted` (код ошибки протокола 5) при превышении.

Значения по умолчанию у сторон различаются, и решает серверное:

| Сторона | По умолчанию | Замечания |
|---------|--------------|-----------|
| Канал сервера (обвязка Spring Boot) | `8` | Адаптер Boot не передаёт `grid.sql.max-tx-contexts` в слушатель |
| Клиент (`grid://`, `RemoteConnectionFactory`) | `256` | Параметр URL или аргумент конструктора |

Поэтому приложение, держащее больше восьми одновременных транзакций на одном соединении, получит отказы, даже если его собственный предел выше. Распределяйте нагрузку по дополнительным экземплярам `Connection` — каждый из них отдельный канал TCP, — а не поднимайте значение на клиенте. Это ограничение числа сессий, а не пул сокетов: параллельные транзакции — это объекты `TxContext`, мультиплексированные в одном канале.

## Граница аутентификации

Кадр AUTH задаёт только аутентификацию канала. Он не решает судьбу коммита: допуск записи и сохранность определяют согласие и журнал — см. [долговременное хранение](durability.md). Писателя клиент находит по метаданным протокола, а не по конфигурации — см. [передачу роли писателя](../operations/ha-promote.md).

| Состояние каталога | Поведение |
|--------------------|-----------|
| Пользователей нет | Создаётся администратор из `grid.sql-server.user`/`password` (по умолчанию `grid`/`grid`) с полными правами; оба пустые → вход без пароля до первого `CREATE USER` |
| Пользователи есть | Учётные данные обязательны в URL; кадры без AUTH отвергаются с `not authenticated` |

Ограничьте сетевой доступ к порту SQL — см. [безопасность](../operations/security.md).

## Проверка при вводе в строй

1. Запустите узел и найдите в логе сообщение о привязке порта SQL.
2. Запросите готовность: `curl http://127.0.0.1:7777/health/readiness` при раскладке из сборки или `/actuator/health/readiness` на стандартном базовом пути Spring.
3. Убедитесь, что в деталях готовности `sqlTcp: listening`. При включённой репликации дождитесь `orchidSynced: true` — до этого готовность остаётся DOWN намеренно.
4. Подключитесь и выполните простейший запрос:

```text
grid://grid:grid@127.0.0.1:15432/public
SELECT 1;
```

Интерактивный клиент описан в [SQL CLI](../../tools/sql-cli.md).

5. Создайте первого пользователя (или учётные записи приложения), выдайте права, смените пароль администратора в проде и переведите клиентов на URL с учётными данными.
6. Только после этого направляйте на узел прикладной или нагрузочный трафик.

## Запуск без Spring Boot

Из среды разработки запускайте `org.genfork.grid.sql.SqlServerMain` с включёнными preview-возможностями. В виде готового артефакта используйте толстый jar модуля `grid-sql-server-starter` с одним из профилей выше.

## Симптом и действие

| Симптом | Причина | Действие |
|---------|---------|----------|
| Отказ соединения на 15432 | Слушатель выключен или привязан к другому интерфейсу | Поставить `grid.sql-server.enabled: true`; проверить `host` |
| `bad frameLen` | Клиент направлен на порт репликации | Использовать порт SQL |
| Готовность DOWN, `reason: sql_tcp_down` | Слушатель включён, но не привязан | Искать конфликт портов в логе запуска |
| Готовность DOWN, `reason: orchid_not_synced` | Репликация ещё не синхронизирована | Подождать, трафик не подавать — [репликация](replication.md) |
| `AUTH failed` | Учётные данные не совпадают с каталогом | Исправить authority в URL — [безопасность](../operations/security.md) |
| `not authenticated` | Кадры отправлены до AUTH при наличии пользователей | Передать учётные данные в URL |
| `maxTxContexts=8 exhausted` | Больше восьми одновременных сессий в одном канале | Открыть дополнительный `Connection` |
| `lock wait timeout` | Блокировку записи держит другая транзакция | Сократить транзакции; пересмотреть `grid.sql.lock-wait-timeout-ms` |
| Два узла на одном хосте не поднимают Actuator | Оба используют порт 7777 | Задать каждому свой `server.port` |

## Ограничения

- Один порт SQL на узел; отдельного порта для JDBC нет, а AUTH, готовность и поиск писателя общие для обоих клиентских интерфейсов.
- Каждому узлу нужен свой каталог данных. Общий каталог на кластер не поддерживается.
- TLS на порту SQL в продукте нет; завершайте его на прокси перед узлом — [безопасность](../operations/security.md).
- Нагрузку и задержки измеряйте реактивным клиентом; JDBC поддерживается, но добавляет собственный блокирующий слой.
