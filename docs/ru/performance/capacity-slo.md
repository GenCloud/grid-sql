# Ёмкость и пороги нагрузки

На лабораторном хосте (два узла, `fsync: true`) Grid держит примерно **4922** записи/с, **59430** чтений/с и **8772…11352** операций/с на смешанной нагрузке. Формальный порог регресса — около 95% опорной цифры, а для полосы — её нижней границы. Мерить на спокойном хосте, по одной проверке за раз, через `grid://`.

Нагрузку подаёт **Apache JMeter** поверх `grid-sql-client`. JDBC уместен в приложениях, но в прогонах ёмкости используется только `grid://`: синхронная обвязка искажает задержки. Jepsen проверяет согласованность, а не пропускную способность.

## Что измеряем

| Профиль | Смесь запросов | Что показывает |
|---------|----------------|----------------|
| **WRITE_ONLY** | UPSERT 100% | Потолок долговечной записи: журнал изменений (*OpLog*) + `fsync` + согласование узлов (*ORCHID*) |
| **READ_ONLY** | EQ 90% / JOIN 10% | Потолок индексного чтения и простого соединения |
| **Capacity QG** | EQ 50 / UPSERT 40 / JOIN 10 | Смешанная нагрузка |
| **Chaos** | то же плюс 20% коротких транзакций | Конфликты блокировок |
| **Stress** | много записи и немного коротких транзакций | Перегрузка |

Отдельно снимается **HA mix sizing** — смесь Capacity на 120 с и 128 потоков; это цифра для планирования, а не рекорд.

| Профиль сервера | Смысл | Годится для порогов |
|-----------------|-------|---------------------|
| **`primary` + `replica`** | HA: ORCHID, реплика, **`fsync: true`** | **Да** — заявленный максимум HA |
| **`capacity`** | Одиночный узел с записью на диск, без репликации | Да, но отдельной цифрой |
| `fsync: false` | Лабораторная изоляция без стоимости OpLog | **Нет** |

Для READ и QG опорное значение — полоса наблюдений: на таких скоростях шум хоста нормален. Формальный порог — ≈95% опорной цифры или нижней границы полосы.

## Как мерить

Спокойный хост, JMeter в режиме CLI (`-n`). Нагрузку нельзя гонять одновременно с QG, Jepsen или JMH. Порядок проверок: [методика](methodology.md).

```powershell
# -Stamp задаёт имя выходных файлов в grid-server-core/benchmarks/lab/
powershell -File .\scripts\run-jmeter-load-slo.ps1 -Stamp <run-id> -Clients 128 -MixProfile WRITE_ONLY
powershell -File .\scripts\run-jmeter-load-slo.ps1 -Stamp <run-id> -Clients 128 -MixProfile READ_ONLY
powershell -File .\scripts\run-jmeter-load-slo.ps1 -Stamp <run-id> -Clients 64 -MixProfile CAPACITY
```

`-Profile` задаёт только `KEY_SPACE` (`capacity` = 1 млн ключей, `contention` = 10 тыс.). Полный список флагов: [JMeter](../tools/jmeter-load-slo.md).

### Хост, на котором получены цифры

| | |
|--|--|
| ОС | Windows 10 Pro 10.0.18362 |
| CPU | Intel Core 7 240H, 10 ядер / 16 потоков |
| RAM | ≈64 ГиБ |
| Диск | NVMe SSD; `dataDir` на локальном `D:` |
| JDK | Temurin 25 (`--enable-preview`) |
| Топология HA | `primary` + `replica` на localhost, `fsync: true` |

Цифры привязаны к этому железу. Для облака, WAN и нескольких площадок нужен отдельный прогон.

## Опорные цифры

HA (`primary` + `replica`, `fsync: true`): запись **4921.975**/с, чтение **52261…59430**/с, QG **8772…11352**/с, HA mix **9013**/с. Пороги: ≈**4676** / ≈**52261** / ≈**8333**.

Одиночный узел (`capacity`): запись **7095**/с, QG **19526**/с, чтение **56564**/с.

| Трек | Потоки | Окно | TPS | p95 | Порог (~95%) |
|------|-------:|-----:|----:|----:|-------------:|
| WRITE_ONLY (HA) | 48 | 40 с | **4921.975** | 14 мс | ≈**4676** |
| READ_ONLY (HA) | 64 | 45 с | **52261…59430** | 1 мс | ≈**52261** |
| Capacity QG (HA) | 64 | 45 с | **8772…11352** | 16…31 мс | ≈**8333** |
| HA mix | 128 | 120 с | **9013** | 43 мс | — |
| WRITE (одиночный узел) | 48 | 40 с | **7095** | 8 мс | — |
| QG (одиночный узел) | 64 | 45 с | **19526** | 7 мс | — |
| READ (одиночный узел) | 64 | 45 с | **56564** | 1 мс | — |
| Chaos | 32 | 40 с | ≈302 | 138 мс | ошибки ≤0.15 |

Удвоение этих цифр не заявлено: во всех прогонах действует `WRITE_BATCH_SIZE=1` по умолчанию.

Наблюдаемый разброс WRITE на этом хосте — ≈**3969…5055**/с; для READ и QG опорное значение и есть полоса.
