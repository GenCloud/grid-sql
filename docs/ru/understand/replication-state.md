# Состояние репликации: память и диск

Репликация включена. Узел перезапустился. Что должно лежать на диске, а что можно собрать заново из журнала и от соседних узлов?

**На диске** — журнал мутаций, номер последнего подтверждённого коммита и данные для восстановления расхождений. **В памяти** — горячий набор строк, индексы и текущий вид живых соседних узлов.

## Раскладка каталогов

Каждый узел пишет в собственный каталог:

```
{data-dir}/{clusterId}/{nodeId}/
        ├── oplog/      журнал мутаций, сегментами
        ├── orchid/     state.bin — номер последнего подтверждённого коммита
        ├── locus/      журнал мест изменений для восстановления
        └── overlay/    пометки PIN, если сохранение включено
```

*Схема 1. Каталог узла: всё, что нужно для восстановления после рестарта.*

Каталог должен быть **локальным для узла**. Один общий сетевой том на весь кластер не поддерживается. Два процесса, направленные в один каталог, портят сегменты друг друга, и обнаруживается это обычно только на следующем рестарте.

Запечатанные файлы карты (`.gmap`, `.sbpt`, `.sbm`) лежат в дереве данных SQL-каталога, см. [хранение](storage-sealed-gmap.md).

### Пути и содержимое

| Путь | Содержимое |
|------|------------|
| `oplog/{hexDomain}_{shard}.log` | Полезные данные мутаций |
| `oplog/*.log.wpos` | Логическая длина записи |
| `oplog/*.meta` | Водяной знак обрезки |
| `orchid/state.bin` | 8-байтовый `lastCommittedSeq`, записывается после подтверждения OpLog |
| `locus/{domain}_{shard}.locus` | Долговременная копия `VersionLocusMap` |
| `sealed/*.gmap` / `.sbpt` / `.sbm` | Запечатанная карта плюс вторичные и bitmap-индексы |
| `index-ckpt/*.meta` | **Водяной знак по ключам** (плюс опциональный CRC) — признак пригодности к перестройке, а не полный дамп дерева из памяти |
| `overlay/*.ovl` | Долговременная копия overlay, если включена |

Устаревшие `map-wal/` и компактные дампы карты `snapshot/*.bin` **удалены**: долговременный путь — OpLog плюс запечатанные файлы.

## Счётчики последовательностей

Четыре счётчика легко перепутать, а отвечают они на разные вопросы.

| Счётчик | Хранение | Смысл |
|---------|----------|-------|
| `orchid.lastCommittedSeq` | диск, `state.bin` | Глобальный счётчик коммитов ORCHID |
| `OpLog.lastSeq(домен, шард)` | диск, oplog | Последний номер мутации этого шарда; пропуски между шардами нормальны |
| `appliedWatermark(домен, шард)` | память | Последний номер, применённый к локальной карте |
| `peerAck(peerId, домен, шард)` | память | Последний полученный от пира `APPLY_ACK` |

Первые два переживают рестарт, последние два собираются заново. Поэтому перезапущенный узел заново выясняет, докуда догнал каждый пир, а не доверяет устаревшему виду.

## Что есть только в памяти

- `GridScalableMap` — рабочий набор горячих ключей, восстанавливается из запечатанных файлов и хвоста журнала.
- Индексы в памяти (B+ tree, bitmap) — ускорители. Их долговременная форма после запечатывания — `.sbpt` и `.sbm`.
- Вид живых пиров и текущие фазы — оперативное состояние, собирается после рестарта заново.
- Изменения, ещё лежащие в очереди записи.

Ничто из этого не является единственной копией данных при включённой записи на диск. Потеря кучи стоит скорости, а не строк.

## Наполнение после рестарта

Последовательность такая: запечатанные файлы карты (плюс `.sbpt` / `.sbm`) → проигрывание OpLog начиная с `водяной_знак + 1` → перестройка индексов либо наполнение от водяного знака по ключам из контрольной точки индекса. B+ tree в памяти — ускоритель; долговременный вторичный индекс — запечатанный `.sbpt`.

Чего точно не вернётся, так это незакоммиченного состояния: транзакция, не дошедшая до `COMMIT`, в журнал не попадала, и после рестарта её просто нет. Это ожидаемо, а не потеря данных.

## Порядок «отказ вместо частичного применения»

Коммит ORCHID происходит **до** появления строки в карте. За добавлением в OpLog следует `confirmPersisted`: на узле-писателе это делает `MutationRecorder`, на пире — `ReplicaApplier`. Путь отправки ждёт разрешения по потоку, а не копит очередь без границ.

Нет подтверждения — нет видимой строки. Пути, при котором отклонённая запись проявилась бы позже, не существует.

## Маркеры транзакций и накопление изменений

Три разных вещи, которые стоит держать раздельно:

| Что | Как хранится |
|-----|--------------|
| Жизненный цикл транзакции | `TX_BEGIN`, `TX_COMMIT`, `TX_ABORT` — записи в OpLog, прошедшие ORCHID (`recordTxMarker`) |
| Изменения строк | Полная цепочка через `MutationRecorder`: ORCHID → OpLog → подтверждение → карта |
| Накопление при применении | `ReplicaApplier` держит операции открытой транзакции до `TX_COMMIT`, затем применяет их как единицу |

Маркеры не заменяют операции со строками: одно без другого не работает. Разбор по шагам — [путь записи](write-path-staging.md).

## Одиночная запись, живые узлы и голосующие

Правила, которые защищают от расхождения данных при разделении сети:

- Одиночная запись разрешена **только** если список настроенных пиров пуст (`peerIds.isEmpty()`, старт с `N = 1`).
- При настроенных `N ≥ 2` и `livePeerCount() == 0` после разделения сети узел **не** считается синхронным. Пустой вид живых пиров не даёт права писать.
- `forgetPeer` очищает вид живых узлов, но **не уменьшает** заданный размер кворума.
- Предлагающий узел выбирается по фазе: `min(nodeId)` среди себя и увиденных пиров.
- Пир возвращается в голосующие, когда его `APPLY_ACK` догонит; HELLO с тем же `clusterId` добавляет его обратно через `addPeer`.

## Готовность восстановления и размещения

| Компонент | Значения по умолчанию | Контракт |
|-----------|----------------------|----------|
| `HomologousRepair` | `homologous-enabled: true`, `reconcile-interval-ms: 5000` | Сверка locus, пересылка диапазона, запрос отдельной строки |
| `AdaptiveReplicaSwarm` | `enabled: true`, `score-window-ms: 5000`, `migrate-threshold: 0.3` | Только подсказки, пока перенос не выполнит `ShardMigrator` |
| Смена владения шардом | — | QUIESCE → CATCH_UP → смена владельца; журнал уходит раньше, чем переезжает владение |

Подробнее: [размещение шардов](overlay-and-swarm.md).

## Что проверять при расхождении

| Симптом | Куда смотреть |
|---------|----------------|
| `repair_issued` растёт, `repair_applied` нет | `HomologousRepair`, диск, водяные знаки — [мониторинг](../configure-and-operate/monitoring.md) |
| Разный номер ORCHID на пирах после подтягивания | Locus и OpLog; убедиться, что нет общего `dataDir` |
| После рестарта «пропали» свежие коммиты | Сверить водяной знак запечатывания с хвостом OpLog; проверить покрытие архива |
| Readiness DOWN после старта | Узел ещё не синхронизирован по ORCHID (`orchidSynced`) |
| Незакоммиченная транзакция исчезла после рестарта | Ожидаемо: грязное состояние до `COMMIT` в журнал не попадает |
| Два писателя после смены площадки | Проверить `regionEpoch` и закрепление клиента — [повышение роли узла](../configure-and-operate/operations/ha-promote.md) |
| Клиент остался на старом писателе | Это не про состояние — [повышение роли узла](../configure-and-operate/operations/ha-promote.md) |

## Чего в этой схеме нет

Нет слияния конкурирующих версий в стиле CRDT, нет биологических имён в публичном API и в YAML, нет пространства настроек `hdcrm.*`, и связывание фаз через WAN не является основным путём согласованности между площадками. Где заканчивается метафора и начинается реализация: [границы утверждений](bio-inspired.md).
