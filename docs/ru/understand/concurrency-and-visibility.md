# Параллелизм и видимость

Когда изменение становится видно другим сессиям, как устроена транзакция и где стоят блокировки. Рядом: [транзакции](../develop/transactions.md), [путь записи](write-path-staging.md), [ORCHID](orchid-consensus.md).

## Автокоммит и открытая транзакция

| Режим | Поведение |
|-------|-----------|
| **Autocommit** | Каждое выражение — отдельная единица. При успехе изменение проходит допуск (ORCHID при durability/репликации) и журнал, и только потом попадает в карту для других сессий. |
| **Открытая TX** (`BEGIN` … `COMMIT` / `ROLLBACK`) | Мутации копятся в грязном буфере (`SqlTxBuffer`) сессии. Снаружи они не видны как зафиксированные, пока `COMMIT` не завершился успешно. |

DDL внутри открытой транзакции **отклоняется**. Схему меняют в autocommit.

`ROLLBACK` отбрасывает грязный буфер. То, что уже попало в OpLog после успешного commit, откатом сессии не отменяется — для отката состояния во времени нужен [PITR](../configure-and-operate/operations/pitr.md).

## Порядок commit при durability / репликации

Успешный `COMMIT` на узле с записью на диск (и с пирами, если репликация включена) означает по порядку:

1. Взяты блокировки записей на затронутые ключи.
2. Допуск ORCHID: фазовая синхронизация и кворум digest по топологии.
3. Запись в OpLog (`fsync` на промышленных профилях).
4. Применение в карту в памяти и постановка в очереди индексов.
5. Только после этого строки видны параллельным читателям как зафиксированные.

Если шаг не прошёл, клиент получает отказ. Частично применённый commit наружу не выставляется — правило из [архитектуры](architecture-overview.md).

## Блокировки записей

SQL-транзакции берут справедливые блокировки на пару `(таблица, ключ)` через `SqlRecordLockManager`.

- Ожидание блокировки идёт на логическом пуле виртуальных потоков, **не** на event loop Netty.
- Конкурирующие ключи сериализуются: на смесях Chaos/Stress растёт p95 — это ожидаемо ([ёмкость](../performance/capacity-slo.md)).
- Блокировка держится на время TX; после `COMMIT` / `ROLLBACK` отпускается.
- Потолок ожидания: `grid.sql.lock-wait-timeout-ms` (по умолчанию `8000`) — дальше клиент получает `lock wait timeout` ([SQL-сервер](../configure-and-operate/configuration/sql-server.md)).

### `FOR UPDATE` и блокировки на пирах

`SELECT … FOR UPDATE` берёт те же блокировки записи, что и путь записи, чтобы параллельная TX не меняла эти ключи до конца текущей. При включённой репликации агенты блокировок на пирах строятся из **`peers` репликации** (не из отдельного SQL-списка) — только локально, если репликация выключена или список пиров пуст. Ошибка Netty на блокировке пира — **отказ при ошибке**, а не тихий только-локальный commit. Подробнее: [чтение с реплики](../configure-and-operate/operations/replica-reads.md).

`FOR UPDATE SKIP LOCKED` пропускает ключи, уже занятые другой TX, вместо ожидания (до `lock-wait-timeout-ms`). Удобно конкурирующим воркерам, которым подойдёт другая строка; не используйте, если нужно удержать каждый выбранный ключ.

## Точки сохранения

Внутри открытой транзакции `savepoint` / `rollbackTo` / `release` меняют только грязный буфер в памяти. Журнал и ORCHID они не трогают. Последовательности не отматываются. Примеры API: [транзакции](../develop/transactions.md).

## Соединение и TxContext

| Понятие | Роль |
|---------|------|
| `Connection` / TCP | Транспорт. Один сокет несёт много логических сессий. |
| `TxContext` | Независимая транзакция и дескриптор PREPARE (`PreparedHandle`). |
| `maxTxContexts` | Мягкий потолок параллельных логических сессий на этом TCP. |

Параллельная работа приложения = несколько `begin()` / `TxContext` на одном соединении, а не отдельный сокет на каждый параллельный поток. Один `ConnectionFactory` (или DataSource) на процесс; при остановке — `dispose()`. На **сервере** по умолчанию канал принимает **8** сессий; Boot не поднимает потолок из YAML — дальше откройте ещё один `Connection` ([SQL-сервер](../configure-and-operate/configuration/sql-server.md)).

`.block()` допустим только на границе приложения (`main`, CLI, тест), не внутри библиотечных reactive-цепочек.

## PREPARE (подготовленные выражения)

`PREPARE` сохраняет исполняемый handle на сессии. Тело берётся из интервала ANTLR char-stream (пробелы сохраняются). Выполнение prepared-выражения подчиняется тем же правилам видимости, что и обычный SQL внутри транзакции.

## Чтение с реплики

Реплика может обслуживать чтения, но **не** гарантирует read-your-writes относительно только что записанного на writer. Если `applyLagStale` — сначала подтягивание, не «лечение» клиентом ([чтение с реплики](../configure-and-operate/operations/replica-reads.md)).

## Границы модели

Видимость в SQL — порядок commit и грязный буфер, без классических MVCC-снимков. Пишет один proposer по фазе; смена роли явная ([повышение роли](../configure-and-operate/operations/ha-promote.md)). XA и двухфазный commit с чужими системами не поддерживаются.
