# Параллелизм и видимость

Два сеанса смотрят на одну строку. Когда второй увидит то, что первый уже закоммитил? Не раньше, чем запись прошла допуск и журнал. Пока транзакция открыта, чужие сессии видят старое состояние — грязный буфер наружу не торчит.

Рядом: [транзакции](../develop/transactions.md), [путь записи](write-path-staging.md), [ORCHID](orchid-consensus.md).

## Autocommit и открытая транзакция

| Режим | Поведение |
|-------|-----------|
| **Autocommit** | Каждое выражение — отдельная единица. При успехе: допуск ORCHID (если запись на диск / репликация) → журнал → карта. |
| **Открытая TX** (`BEGIN` … `COMMIT` / `ROLLBACK`) | Мутации копятся в грязном буфере сессии. Снаружи не видны как зафиксированные, пока `COMMIT` не прошёл. |

DDL внутри открытой транзакции **отклоняется**. Схему меняют в autocommit.

`ROLLBACK` отбрасывает грязный буфер. То, что уже попало в журнал после успешного commit, откатом сессии не отменяется — для отката во времени нужен [PITR](../configure-and-operate/operations/pitr.md).

## Порядок commit при записи на диск

Успешный `COMMIT` на узле с диском (и с соседними узлами, если репликация включена) означает по порядку:

1. Взяты блокировки записей на затронутые ключи.
2. Допуск ORCHID: фаза и контрольная сумма по большинству из конфигурации.
3. Запись в OpLog (`fsync` на рабочих профилях).
4. Применение в карту и очереди индексов.
5. Только после этого строки видны параллельным читателям как зафиксированные.

Если шаг не прошёл — отказ клиенту. Частично применённый commit наружу не выставляется. Лучше отказ, чем «половина в карте».

## Блокировки записей

SQL-транзакции берут справедливые блокировки на пару `(таблица, ключ)`.

- Ожидание идёт на логическом пуле виртуальных потоков, **не** на event loop Netty.
- Конкурирующие ключи сериализуются: на смесях Chaos/Stress растёт p95 — это ожидаемо ([ёмкость](../performance/capacity-slo.md)).
- Блокировка держится на время TX; после `COMMIT` / `ROLLBACK` отпускается.
- Потолок ожидания: `grid.sql.lock-wait-timeout-ms` (по умолчанию `8000`) — дальше клиент получает `lock wait timeout` ([SQL-сервер](../configure-and-operate/configuration/sql-server.md)).

### `FOR UPDATE` и блокировки на соседних узлах

`SELECT … FOR UPDATE` берёт те же блокировки, что и путь записи, чтобы параллельная TX не меняла эти ключи до конца текущей. При включённой репликации агенты блокировок на соседних узлах строятся из **`peers` репликации** (не из отдельного SQL-списка) — только локально, если репликация выключена или список пуст. Ошибка Netty на блокировке соседа — **отказ клиенту**, а не тихий только-локальный commit. Подробнее: [чтение с реплики](../configure-and-operate/operations/replica-reads.md).

`FOR UPDATE SKIP LOCKED` пропускает ключи, уже занятые другой TX, вместо ожидания. Удобно конкурирующим рабочим, которым подойдёт другая строка; не используйте, если нужно удержать каждый выбранный ключ.

## Точки сохранения

Внутри открытой транзакции `savepoint` / `rollbackTo` / `release` меняют только грязный буфер в памяти. Журнал и ORCHID они не трогают. Последовательности не отматываются. Примеры API: [транзакции](../develop/transactions.md).

## Соединение и TxContext

| Понятие | Роль |
|---------|------|
| `Connection` / TCP | Транспорт. Один сокет несёт много логических сессий. |
| `TxContext` | Независимая транзакция и дескриптор PREPARE (`PreparedHandle`). |
| `maxTxContexts` | Мягкий потолок клиента на параллельные логические сессии на этом TCP (по умолчанию **256**); на сервере жёсткий потолок **8** — при исчерпании откройте ещё один `Connection`. |

Параллельная работа приложения = несколько `begin()` / `TxContext` на одном соединении, а не отдельный сокет на каждый параллельный поток. Один `ConnectionFactory` (или DataSource) на процесс; при остановке — `dispose()`. На **сервере** по умолчанию канал принимает **8** сессий; Boot не поднимает потолок из YAML — дальше откройте ещё один `Connection` ([SQL-сервер](../configure-and-operate/configuration/sql-server.md)).

`.block()` допустим только на границе приложения (`main`, CLI, тест), не внутри библиотечных реактивных цепочек.

## PREPARE (подготовленные выражения)

`PREPARE` сохраняет исполняемый handle на сессии. Тело берётся из интервала ANTLR char-stream (пробелы сохраняются). Выполнение prepared-выражения подчиняется тем же правилам видимости, что и обычный SQL внутри транзакции.

## Чтение с реплики

Реплика может обслуживать чтения, но **не** гарантирует «сразу увидеть свою запись» относительно только что закоммиченного на пишущем. После успешного `COMMIT` на пишущем реплика ещё может отдать прежнюю строку, пока не применит этот unit журнала — это отставание применения, а не ошибка клиента.

| Нужно | Куда читать |
|-------|-------------|
| Сразу увидеть свою запись | Закрепление на пишущем (по умолчанию для открытой TX / DML; или предпочтение `PRIMARY`) |
| Масштабировать только чтение SELECT/EXPLAIN | Эндпоинты реплик, пока `applyLagStale` false |
| Реплика с `applyLagStale` | Сначала подтягивание — не «лечить» отставание в клиенте |

Маршрутизация: [чтение с реплики](../configure-and-operate/operations/replica-reads.md).

## Чего модель не обещает

Видимость в SQL — порядок commit и грязный буфер, без классических MVCC-снимков. Пишет один узел по фазе; смена роли явная ([повышение роли](../configure-and-operate/operations/ha-promote.md)). XA и двухфазный commit с чужими системами не поддерживаются.
