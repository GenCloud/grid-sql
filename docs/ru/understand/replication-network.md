# Сеть репликации

Узлы обмениваются журналом мутаций (*OpLog*) по Netty (`NettyReplicationTransport`). Другого транспорта нет: и внутри дата-центра, и между дата-центрами используется один и тот же канал. OpLog и состояние ORCHID всегда лежат на диске в каталоге `op-log.data-dir`.

В демонстрационной конфигурации репликация слушает порты **5615** (primary) и **5616** (replica), SQL — **15432** и **15433**.

**Не слать SQL на 5615/5616.** Там идут кадры репликации, и SQL-клиент получит `bad frameLen`. Приложения работают с SQL-портом. Разбор инцидентов: [отказы](../configure-and-operate/operations/failures.md).

## Путь изменения

```
MutationRecorder
      │
   ORCHID: фазы + согласие по digest
      │
   OpLog: append + подтверждение записи
      │
   put в карту (строка становится видимой)
      │
   отправка пирам по Netty
      │
   ReplicaApplier на пире → карта пира
```

*Схема 1. Отправка пирам — последний шаг, а не первый.*

Два похожих по звучанию механизма стоит развести:

| Механизм | Что рассылает |
|----------|---------------|
| Репликация | Операции журнала пирам: `UPSERT`, `DELETE`, маркеры транзакций |
| MapReduce по шардам (`DistributedKeyFanOut`) | Раскладывает **локальные ключи шардов** по потокам одного узла для тяжёлых SELECT |

Второе не является рассылкой SQL по пирам. Старый режим, когда одинаковый запрос отправлялся всем узлам, считается устаревшим и выключен.

## Кадры протокола

```
uint32 BE length | uint8 opcode | тело
```

| Семейство опкодов | Назначение |
|-------------------|------------|
| `HELLO` | Знакомство; пир с тем же `clusterId` добавляется в список пиров |
| `OPLOG_PUSH` / `OPLOG_PULL` | Отправка журнала и диапазоны подтягивания |
| `APPLY_ACK` / `APPLY_NACK` | Подтверждение пиром применённых номеров операций |
| `ORCHID_*` | Обмен фазами, предложения, рассылка коммита |
| `REPAIR_*` | Сверка locus, пересылка диапазона, запрос отдельной строки |

Это внутренний двоичный протокол между узлами. Он не доступен приложениям, не является SQL-протоколом, и HTTP-API статуса репликации для опроса не существует.

## Внутри дата-центра

Отправка происходит **асинхронно**, уже после того как запись подтверждена на узле-писателе. Поэтому видимость на реплике отстаёт — это и описывают режим чтения `eventual_replica` и метрика `maxApplyLag`.

| Уровень | Гарантия |
|---------|----------|
| Писатель (предлагающий узел по фазе) | ORCHID и OpLog **до** видимости в карте, поэтому сессия читает собственные записи |
| Локальный пир (реплика) | Асинхронная отправка, затем применение; режим чтения `eventual_replica` |
| RPO | Ненулевой, пока операции в пути или ещё не применены: от долей миллисекунды до десятков миллисекунд на спокойном хосте, больше под нагрузкой или при отставании пира |
| Пустая реплика при старте | Ожидаемо до завершения подтягивания; начальная загрузка данных выполняется только на профиле primary |

Отставание — ожидаемая цена такой схемы, а не ошибка применения. Приложение, читающее с реплики, должно быть к этому готово, включая отказ, когда устаревание превысит `maxStaleLag`: [чтение с реплики](../configure-and-operate/operations/replica-reads.md).

**Не баг:** короткое окно, когда только что записанного ключа на реплике ещё нет.
**Баг:** устойчивое расхождение после того, как отставание дошло до нуля и восстановление отработало, — разница контрольных сумм или отсутствующий ключ при равных водяных знаках.

## Применение на пире

`ReplicaApplier` буферизует `UPSERT` и `DELETE` между `TX_BEGIN` и `TX_COMMIT` и применяет их одним куском, поэтому читатель на реплике не видит половины транзакции. При применении пир пишет собственный OpLog: реплика — долговременная копия, а не кэш писателя.

Дыры и расхождения закрывает `HomologousRepair`: он сверяет контрольные суммы по журналу мест изменений и при необходимости запрашивает пересылку диапазона или отдельной строки. Само владение шардом тоже может переезжать между узлами — за это отвечают `AdaptiveReplicaSwarm` и `ShardMigrator`, см. [размещение шардов](overlay-and-swarm.md).

## Между дата-центрами

За рассылку в удалённые площадки отвечает `CrossDcPublisher`. Есть два режима:

| Режим | Поведение |
|-------|-----------|
| `ASYNC_SHIP` | Изменения уходят в удалённые дата-центры асинхронно. Локальный коммит их не ждёт |
| `SYNC_VOTERS_ACROSS_DC` | Указанные удалённые узлы становятся голосующими по digest: коммит ждёт их подтверждения с таймаутом. Узлы только подтягивания (`cross-dc.learners`) остаются асинхронными |

Во втором режиме удалённые узлы участвуют **только** в согласии по digest. Их фазы не входят в локальный параметр порядка `R`, пока связывание фаз через WAN не включено явно, а по умолчанию оно выключено.

Размен простой: `ASYNC_SHIP` оставляет задержку коммита локальной и принимает межплощадочный RPO, а `SYNC_VOTERS_ACROSS_DC` платит обращением через WAN на каждой записи, чтобы этот RPO сократить. Развёртывание и выбор режима: [несколько ЦОД](../configure-and-operate/operations/multi-dc.md).

## Настройки

```yaml
grid.replication:
  orchid:
    coupling: 15.0
    natural-freq-hz: 1.0
    order-threshold: 0.85
    tick-ms: 10
    digest-quorum: MAJORITY
  repair:
    homologous-enabled: true
    reconcile-interval-ms: 5000
  swarm:
    enabled: true
    score-window-ms: 5000
    migrate-threshold: 0.3
  placement-optimizer:
    enabled: true
  transport:
    bind-host: 127.0.0.1
    bind-port: 5615
    peers:
      - { id: replica-1, host: 127.0.0.1, port: 5616, dc: dc-a }
  cross-dc:
    enabled: true
    local-dc: dc-a
    mode: ASYNC_SHIP        # либо SYNC_VOTERS_ACROSS_DC
    phase-coupling: false   # выкл: фазы удалённых узлов не входят в локальный R
    remote-ack-timeout-ms: 5000
    voters: []              # синхронные голосующие при SYNC_VOTERS_ACROSS_DC
    learners: []            # только асинхронное подтягивание
  op-log:
    data-dir: ./data/replication
    fsync: true
```

Соблюдайте `2 * pi * natural-freq-hz * tick-ms / 1000 ≪ 1` — почему именно так, объясняет страница [ORCHID](orchid-consensus.md).

Ключей с префиксом `hdcrm.*` в конфигурации **нет**. Размещение настраивается через `swarm` и `placement-optimizer`. Полное описание параметров: [репликация](../configure-and-operate/configuration/replication.md).

## Наблюдаемость

Репликация показывает себя через детали проверок здоровья и метрики, а не через отдельную ручку статуса:

- Детали Actuator `/health/liveness` и `/health/readiness`: `orchidR`, `repairIssued` / `repairApplied`, `rpoEstimateMs`, `swarmHint`, `writerEligible`.
- Датчики Micrometer: `grid.replication.orchid_r`, `repair_*`, `rpo_estimate_ms`, `swarm_hint`.
- `ReplicationMetrics`: счётчики отправок и подтверждений, `orchidWaitP50/P99Ns`, `oplogFsyncP50/P99Ns`, счётчики duplex.

Сверка digest мест изменений между узлами — действие оператора через SQL TCP и административные инструменты, а не REST-обнаружение. Клиенты никогда не ищут писателя по HTTP: для этого есть `ServerMeta` и `PROMOTE_NOTIFY`. Дашборды и пороги: [мониторинг](../configure-and-operate/monitoring.md).

## Как это выглядит при сбое

| Ситуация | Что происходит |
|----------|----------------|
| Пишущий узел недоступен | Клиент заново находит подходящего писателя по `PROMOTE_NOTIFY` / AUTH — [повышение роли узла](../configure-and-operate/operations/ha-promote.md) |
| Реплика отстаёт | `maxApplyLag` растёт; SELECT на реплике может быть отклонён при превышении `maxStaleLag` — [чтение с реплики](../configure-and-operate/operations/replica-reads.md) |
| Пир упал и вернулся | Подтягивание отправляет недостающий диапазон; полная пересылка журнала не нужна |
| Дыра в OpLog | `HomologousRepair` и разреженное подтягивание присылают диапазон, а не весь журнал |
| Witness в схеме с несколькими ЦОД | Участвует в изоляции площадок, но не держит роль Active-писателя |
| SQL ушёл на 5615 | `bad frameLen`: это порт репликации, а не SQL TCP |
