# Хранение: запечатанные файлы карты

Рестарт при включённой записи на диск. Куча «пустая» — это катастрофа или норма? При `hydrate-mode: LAZY` — норма: истина на диске в журнале (*OpLog*) и в запечатанных файлах, а память держит только горячий набор.

Порядок жёсткий: сначала журнал, затем запечатывание группы изменений в файлы, и только потом обрезка журнала. Карта в памяти — ускоритель, не хранилище. Подробнее настройки: [долговременное хранение](../configure-and-operate/configuration/durability.md).

## Как данные разделяются

Ключ принадлежит ровно одному шарду своей таблицы: `шард = fastHash(ключ) % число_шардов`. Шард — единица почти всего остального: потоки журнала ведутся по паре `(домен, шард)`, запечатанные файлы создаются на шард и узел, единицы коммита помечаются как `table#шард`, а размещение переносит владение по одному шарду.

Внутри шарда строка — упакованная двоичная запись с таблицей смещений в конце. Слой хранения ничего не знает о колонках как о полях Java: он знает смещения, длины и каталог, который сопоставляет имени колонки одно из них.

## Артефакты на диске

| Артефакт | Роль |
|----------|------|
| OpLog | Журнал мутаций. Коммит считается состоявшимся только после записи в журнал; после запечатывания журнал обрезается по водяному знаку |
| `{домен}_{шард}_n{узел}.gmap` | Неизменяемый файл узла: каталог (корзины), отображение «ключ → смещение» и сами полезные данные |
| `*.sbpt` | Запечатанный вторичный B+ tree с фиксированной страницей. Новые файлы — **VERSION 2** (знаковое сравнение INT/LONG); **VERSION 1** при чтении отклоняется — нужен reseal / `dumpDomain` |
| `*.sbm` | Запечатанный bitmap-индекс |
| `index-ckpt/*.bytes` | Водяной знак по ключам плюс CRC. Это **не** полный дамп индекса из памяти: после запечатывания вторичные индексы лежат в `.sbpt` |
| `orchid/state.bin` | Глобальный номер последнего подтверждённого коммита |
| `locus/` | Сопроводительные данные для восстановления расхождений (`HomologousRepair`) |

Маркеры снимков хранят только диапазоны OpLog для наполнения; дампа карты в них нет.

Устаревшие механизмы — WAL поверх карты и двойная запись компактных снимков — удалены. Если по старым заметкам вы ищете каталог `map-wal/` или файл `snapshot/*.bin`, их больше нет.

## Что внутри файла `.gmap`

Файл узла пишется один раз и никогда не изменяется. В нём три области:

1. **Каталог** — массив корзин, отображающий хеш ключа в цепочку слотов. Именно он превращает точечное чтение в поиск по хешу, а не в перебор.
2. **Таблица «ключ → смещение»** — для найденного слота точная позиция и длина полезных данных.
3. **Полезные данные** — упакованные байты строк, уложенные подряд.

Поскольку файл неизменяем, более позднее изменение того же ключа его не правит. Новая версия проходит через журнал и попадает в следующее поколение запечатанных файлов; путь чтения первым находит самую свежую версию. Место из-под вытесненных версий освобождается при повторном запечатывании шарда, а не на месте.

## Чтение

```
запрос
  │
  ├─► очередь записи (ещё не слитые изменения)
  │
  ├─► карта в памяти (рабочий набор)
  │
  ├─► запечатанный индекс .sbpt
  │
  └─► файл узла .gmap  (промах в памяти → подгрузка ключа)
```

*Схема 1. Порядок поиска строки: от самого свежего к самому холодному.*

### Промах рабочего набора

Когда ключа нет в `GridScalableMap`, чтение не останавливается и не запускает полный обход раздела:

1. Сначала смотрят вторичный запечатанный индекс (`.sbpt` / `.sbm`), если запрос идёт по индексу.
2. При попадании в индекс или при чтении по первичному ключу открывают нужное **окно mmap** в файле узла `.gmap` и читают полезные данные по смещению.
3. Подтянутый ключ может вернуться в рабочий набор; при следующем обращении диск не нужен, пока ключ не вытеснят.

**Промах индекса не превращается в полный скан.** Если запечатанный индекс не нашёл ключ, ответ пустой (`sealedPartitionScan = 0`), перебора всех партиций не будет. Если эта метрика растёт, это дефект, а не вопрос настройки.

Дамп содержимого домена для диагностики: `SealedGridMapService.dumpDomain`.

## Как файлы отображаются в память

По умолчанию используется **оконный mmap**: отображается окно размером `WINDOW_BYTES`, а не весь файл. Постоянное отображение всех полезных данных включается, только если они целиком помещаются в одно окно. Прежнего порога на весь файл больше нет, поэтому большой запечатанный корпус не означает большого постоянного резерва адресного пространства.

Каталог файла узла тоже отображается лениво: `openShard` держит пути до первого промаха по этому узлу, так что открытие шарда с многими поколениями файлов дёшево, пока из них реально ничего не читают.

Жизненный цикл блокировок устроен так, чтобы не задерживать ни SQL, ни сеть:

- `readLock` — только вокруг получения значения и отображения окна;
- `writeLock` — только вокруг закрытия и снятия отображения.

Ни одну из этих блокировок нельзя держать во время исполнения SQL, ожидания кворума или ожидания на сетевом потоке Netty. Именно это ограничение не даёт медленному диску превратиться в остановленный цикл событий.

## Запечатывание и обрезка журнала

1. Мутации сначала попадают в OpLog; до подтверждения журналом ничего не видно.
2. Фоновое запечатывание упаковывает диапазон ключей в файлы узлов `sealed/{домен}_{шард}_n{узел}.gmap` (и `.sbpt` / `.sbm`, если такие индексы есть) и поднимает водяной знак.
3. После успешного запечатывания журнал можно обрезать **по водяному знаку**, и живой хвост OpLog остаётся коротким. При включённом архиве для восстановления на точку во времени диапазон сначала копируется в архив, а ошибка копирования отменяет обрезку.
4. Промах рабочего набора теперь читает запечатанные файлы, промах вторичного индекса идёт в `.sbpt`.

Рост каталога `sealed/` после нагрузки и укорочение OpLog после запечатывания — нормальный цикл, а не «потеря журнала».

## Холодный старт

Два режима наполнения задаются параметром `hydrate-mode`:

| Режим | Что происходит | Цена |
|-------|----------------|------|
| `FULL` | Запечатанные файлы и хвост журнала предварительно загружаются в память, индексы перестраиваются | Медленнее старт, больше памяти, рабочий набор тёплый сразу |
| `LAZY` | Запечатанные файлы отображаются в память, читается только хвост журнала; промах подгружает нужные ключи | Быстрый старт, память растёт вместе с трафиком, первое обращение к холодному ключу идёт на диск |

Общая последовательность: запечатанные файлы (`.gmap` плюс `.sbpt` / `.sbm`) → проигрывание хвоста OpLog → перестройка индексов. Либо, если есть контрольная точка индекса, наполнение от её водяного знака по ключам.

`SnapshotService` работает только с диапазонами OpLog. Контрольная точка индекса **не** восстанавливает индекс в памяти целиком — она лишь говорит, до какого места ключи уже запечатаны.

В эксплуатации обычно выбирают `LAZY`: большой запечатанный корпус в режиме `FULL` означает долгий старт и реальный риск нехватки памяти. `FULL` уместен, когда запечатанных данных немного и нужна предсказуемая задержка с первого же запроса после рестарта.

## Рабочий набор и вытеснение

Параметр `working-set-max-entries` (значение больше нуля) включает вытеснение по LRU для холодных закоммиченных ключей. Грязные строки и всё, что ещё лежит в очереди записи, не вытесняются никогда: вытеснение не должно уметь выбросить изменение, не дошедшее до журнала. Вытесненный ключ при следующем обращении подгружается из запечатанных файлов.

Выбор значения — размен памяти на промахи:

- Слишком много — куча тащит холодные ключи, которые никто не читает.
- Слишком мало — рабочий набор, который поместился бы, начинает платить промахом на каждом обращении.
- Честный сигнал — доля попаданий в рабочий набор вместе с задержкой чтения, а не число записей само по себе.

## Рост диска и давление запечатывания

| Наблюдение | Смысл | Что делать |
|------------|-------|------------|
| `sealed/` растёт после длительной записи | Нормальная упаковка | Заложить диск под запечатанные файлы, OpLog и архив; рост сам по себе не повреждение |
| OpLog остаётся большим и не укорачивается | Запечатывание или обрезка застряли; архивный ввод-вывод может блокировать обрезку | Смотреть настройки записи на диск, свободное место, ошибки архива — [долговременное хранение](../configure-and-operate/configuration/durability.md) |
| Диск почти заполнен | Запись, запечатывание и архив могут падать | Освободить место до продолжения; при порванном журнале остановить запись и восстанавливать на копии |
| Промах индекса запускает полный скан партиции | С запечатанным `.sbpt` так быть не должно | Считать дефектом; смотреть метрику `sealedPartitionScan` |

Ёмкость диска планируют сразу под три вещи: запечатанный корпус, живой хвост OpLog и, если включено восстановление на точку во времени, архив. Именно архив растёт без верхней границы, пока его не ротируют.

## Когда пора к восстановлению

Перед сменой хоста, при сомнении в состоянии диска или после аварии с порванным хвостом OpLog: снять или восстановить запечатанную **базу** и проверить покрытие архива за водяным знаком. Обычный цикл запечатывания не требует базы на каждый рестарт.

Процедуры: [резервное копирование и восстановление](../configure-and-operate/operations/backup-restore.md), [восстановление на точку во времени](../configure-and-operate/operations/pitr.md).
