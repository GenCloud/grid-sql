# Основы SQL

Grid использует **Simplified SQL** — намеренно ограниченный диалект, которого хватает и на доступ по ключу, и на аналитику по тем же данным: схема, запись строк, выборки с фильтрами и соединениями, оконные функции, транзакции, индексы. Это не полная копия чужого SQL-диалекта.

Разбор идёт **только через ANTLR**: грамматика `SimplifiedSql.g4` → типизированный оператор. Ручного разбора ключевых слов в ядре нет, восстановления после ошибки тоже: оператор, которого нет в грамматике, отклоняется до обращения к данным, а не исполняется частично.

Точный перечень принимаемых форм — в [поддерживаемых конструкциях](support-matrix.md).

## Как оператор проходит через сервер

| Шаг | Что происходит | Классы |
|-----|----------------|--------|
| 1. Приём | Клиент шлёт текст SQL и параметры по `grid://` | `RemoteConnectionFactory`, `SqlServer` |
| 2. Разбор | Грамматика ANTLR → типизированный `Stmt` | `SimplifiedSql.g4`, `SqlStatementParser` |
| 3. Каталог | Имена таблиц и колонок сверяются со схемой | `TableCatalog`, `TableSchema` |
| 4. План | Фильтры сворачиваются в дерево условий, выбирается стратегия чтения | `QueryOptimizer`, `query.plan.strategy` |
| 5. Исполнение | Чтение из памяти и запечатанных файлов, мутации — в очередь записи | `SqlEngine`, `TableStore` |
| 6. Выдача | Результат отдаётся окнами | `SqlResult` |

Строка внутри сервера — бинарный blob, а не Java-объект. Поля читает `LogicalFieldCursor` по смещениям, ключи соединений, фильтров и индексов остаются байтами до самой границы результата. Поэтому Grid не нужны классы-сущности: схема задаётся в каталоге, а не в коде приложения.

## Чего ожидать от диалекта

| Область | Поведение |
|---------|-----------|
| Совместимость | Подмножество SQL. Не полный диалект другого движка |
| DDL | Таблицы, колонки, ограничения, индексы, схемы, последовательности, представления, функции, триггеры, пользователи и роли |
| DML | `INSERT`, `UPSERT`, `UPDATE`, `DELETE`, `MERGE`, `ON CONFLICT`, `RETURNING` |
| SELECT | Фильтры, `JOIN … ON a = b`, `GROUP BY`, `HAVING`, `ORDER BY`, `LIMIT`/`OFFSET`, `DISTINCT`, `UNION`/`INTERSECT`/`EXCEPT`, `WITH`, оконные функции |
| Транзакции | `BEGIN`/`COMMIT`/`ROLLBACK`, `SAVEPOINT`. До `COMMIT` изменения видит только сама транзакция. DDL внутри открытой транзакции отклоняется |
| Подготовленные операторы | `PREPARE имя AS <оператор>` / `EXECUTE` / `DEALLOCATE`, позиционные параметры `?` |
| Индексы | `CREATE INDEX`, `CREATE UNIQUE INDEX`, `CREATE BITMAP INDEX` — битовый только этой явной командой |
| EXPLAIN | `EXPLAIN` и `EXPLAIN ANALYZE`, текст строит `SqlExplainService` |
| Типы | Набор скалярных `SqlType`: без пользовательских типов и массивов |

Три ограничения определяют почти всю повседневную работу: выражения не вычисляются ни в списке выборки, ни в фильтре; `WHERE` обязателен в `UPDATE` и `DELETE`; идентификаторы пишутся без кавычек. Остальное — в [поддерживаемых конструкциях](support-matrix.md).

### PREPARE

Тело `PREPARE` берётся из исходного текста SQL с сохранением пробелов, а не из склеенных токенов. Параметры — только позиционные `?`. Имя хранится в сессии (`TxContext` или JDBC-соединение): другая TCP-сессия его не видит. `DEALLOCATE` снимает имя, а отключение снимает все подготовленные операторы этой сессии.

## Первые операторы

Схема, одна строка, чтение:

```sql
CREATE TABLE IF NOT EXISTS demo (
  id     BIGINT PRIMARY KEY,
  name   VARCHAR,
  active BOOLEAN
);

UPSERT INTO demo (id, name, active) VALUES (1, 'первая', true);

SELECT id, name FROM demo WHERE id = 1;
```

Параметры вместо литералов:

```sql
SELECT id, name FROM demo WHERE active = ? AND id > ?;
```

Что собирается сделать планировщик:

```sql
EXPLAIN SELECT id, name FROM demo WHERE active = true ORDER BY id LIMIT 100;
```

Несколько операторов в одной транзакции:

```sql
BEGIN;
UPDATE demo SET name = 'вторая' WHERE id = 1;
UPSERT INTO demo (id, name, active) VALUES (2, 'третья', false);
COMMIT;
```

До `COMMIT` изменения видит только эта транзакция. `ROLLBACK` отбрасывает их целиком.
