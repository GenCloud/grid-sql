# Типы

Набор типов маленький и намеренно скалярный. Опорный перечень — `org.genfork.grid.catalog.SqlType` из модуля `grid-commons`: один и тот же enum используют сервер и клиент, поэтому расхождений между «типом в каталоге» и «типом в кадрах протокола» не бывает.

## Таблица соответствий

| Токены в DDL | `SqlType` | Что видит клиент |
|--------------|-----------|------------------|
| `INT`, `INTEGER` | `INT` | `Integer` |
| `BIGINT`, `LONG` | `BIGINT` | `Long` |
| `DOUBLE`, `FLOAT`, `REAL` | `DOUBLE` | `Double` |
| `BOOLEAN`, `BOOL` | `BOOLEAN` | `Boolean` |
| `VARCHAR`, `STRING`, `TEXT`, `JSON` | `VARCHAR` | `String` |
| `TIMESTAMP`, `DATETIME` | `TIMESTAMP` | `String` (ISO-8601) |
| `BYTES`, `BYTEA`, `BINARY`, `BLOB` | `BYTES` | `byte[]` |
| `UUID` | `UUID` | `java.util.UUID` |
| `DATE` | `DATE` | `LocalDate` |
| `TIME` | `TIME` | `LocalTime` |
| `TIMESTAMPTZ`, `TIMESTAMP WITH TIME ZONE` | `TIMESTAMPTZ` | `Instant` |

Токены регистронезависимы. Несколько синонимов ведут к одному `SqlType` — чтобы распространённые имена типов в схемах переносились без переписывания каждой строки.

## Числа

`INT` — 32 бита, `BIGINT` — 64 бита. `DOUBLE` — число с плавающей точкой двойной точности; `FLOAT` и `REAL` попадают туда же, отдельной одинарной точности нет.

Типа с фиксированной точностью (`DECIMAL`, `NUMERIC`) нет. Для денег берите `BIGINT` в минимальных единицах — копейках, центах — и форматируйте на стороне приложения. Это надёжнее, чем `DOUBLE`, и быстрее любой десятичной арифметики.

## Строки и JSON

`VARCHAR` без ограничения длины: длина не объявляется и не проверяется. `STRING` и `TEXT` — синонимы.

`JSON` тоже сводится к `VARCHAR` и хранится как непрозрачный текст UTF-8. Grid не разбирает JSON, не валидирует его и не умеет искать по путям внутри документа. Если нужны фильтры по полю — вынесите поле в отдельную колонку.

`JSONB` отклоняется явной ошибкой: бинарного JSON с внутренней структурой в хранилище нет, и молча подменять его на текст было бы враньём.

## Время и дата

Временных типов четыре, и выбор между ними имеет значение.

| Тип | Представление | Когда брать |
|-----|---------------|-------------|
| `TIMESTAMPTZ` | `Instant`, бинарно, UTC | Момент времени. Предпочтительный вариант для новых схем |
| `DATE` | `LocalDate`, бинарно | Календарная дата без времени |
| `TIME` | `LocalTime`, бинарно | Время суток без даты |
| `TIMESTAMP` | Строка ISO-8601 | Совместимость со старыми схемами |

`TIMESTAMP` остаётся текстом в кадрах протокола ради совместимости с уже запечатанными строками. Он занимает больше места и сравнивается как строка. В новых таблицах используйте `TIMESTAMPTZ`.

Литералы пишутся с префиксом типа:

```sql
SELECT * FROM events
  WHERE day = DATE '2026-09-22'
    AND at  >= TIMESTAMPTZ '2026-09-22T10:00:00Z';
```

## UUID

`UUID` — фиксированные 16 байт, а не строка из 36 символов. Сравнение и индексирование идут по байтам.

```sql
CREATE TABLE sessions (id UUID PRIMARY KEY, user_id BIGINT);
UPSERT INTO sessions (id, user_id) VALUES (UUID '3f2504e0-4f89-11d3-9a0c-0305e82c3301', 42);
```

## Байты

`BYTES` (он же `BYTEA`, `BINARY`, `BLOB`) хранит произвольный массив байтов и на клиенте становится `byte[]`. Это правильное место для сжатых полезных нагрузок, сериализованных сообщений и картинок небольшого размера. Фильтры по содержимому работают только как сравнение на равенство целиком.

## NULL

Любая колонка без `NOT NULL` допускает `NULL`. Проверка — операторами `IS NULL` и `IS NOT NULL`; сравнение `= NULL` не даст ожидаемого результата, как и в любом другом SQL.

Колонка, добавленная через `ALTER TABLE ADD COLUMN`, у ранее записанных строк читается как `NULL`.

## Приведение типов

```sql
SELECT CAST('42' AS BIGINT) FROM demo WHERE id = 1;
```

`CAST` работает на значениях в пределах перечисленного набора типов. Неявных приведений между несовместимыми типами при сравнении не происходит: сравнивайте колонку со значением того же типа, иначе получите ошибку, а не тихо пустой результат.

| Работает | Не работает молча |
|----------|-------------------|
| `CAST('42' AS BIGINT)`, совместимые скаляры | `WHERE int_col = '42'` без CAST (ошибка типа) |
| Литералы с префиксом `DATE '…'`, `UUID '…'` | Смешение `TIMESTAMP` (строка) и `TIMESTAMPTZ` (Instant) как «одного типа» |

На проводе и в индексе ключ — байты `SqlType`. На клиенте (reactive `SqlResult` или JDBC `ResultSet`) — объекты из таблицы соответствий. Менять тип колонки без пересоздания (`ALTER … TYPE`) нельзя: нужны новая колонка и перенос данных приложением.

## Что видит клиент

Результат приходит окнами `SqlResult`. Для каждой колонки есть метаданные: имя и `SqlType`. Значения отдаются как Java-объекты из правой колонки таблицы выше.

Важная деталь про внутреннее устройство: объектами значения становятся **только на границе** результата. Внутри сервера строка — бинарный blob, поля читаются курсором по смещениям, ключи фильтров, соединений и индексов остаются байтами. Поэтому добавление колонки не заставляет переписывать данные, а выборка двух колонок из широкой таблицы не разбирает строку целиком.

JDBC-клиент поверх тех же типов описан в [JDBC-клиент](../develop/jdbc-tooling.md).
