# Индексы

Вторичные индексы объявляются в SQL и хранят указатели на закодированные поля строк. В индексе лежат не копии значений и не сами строки, а ссылки: ключ ищется по индексу, строка достаётся из хранилища.

## Создание

```sql
CREATE INDEX idx_t_name ON t (name);                 -- обычный
CREATE INDEX idx_t_a_b ON t (a, b);                  -- составной
CREATE UNIQUE INDEX uq_t_email ON t (email);         -- с проверкой уникальности
CREATE BITMAP INDEX idx_t_flag ON t (flag);          -- только по явной команде

DROP INDEX idx_t_name ON t;
```

## Три вида

| Вид | `IndexType` | Структура | Смысл |
|-----|-------------|-----------|-------|
| Обычный | `LAX` | `GridPointerBPTree` или `GridPointerCompositeBPTree` | Дубликаты значений разрешены |
| Уникальный | `STRICT` | То же дерево + проверка уникальности | Повтор значения отклоняется при записи |
| Битовый | `BITMAP` | `GridBitmapIndex` внутри `GridCompositeIndex` | Колонка малой мощности |

`LAX` и `STRICT` отличаются только отношением к дубликатам. Это не «строгий режим SQL» и не уровень изоляции — не путайте с ключевым словом `STRICT` из других СУБД.

### LAX — по умолчанию

Обычный `CREATE INDEX` даёт `LAX`. Значения могут повторяться, одному ключу индекса соответствует набор строк. Это правильный выбор для колонок вроде `customer_id`, `status_code`, `created_at`.

### STRICT — уникальность

`CREATE UNIQUE INDEX` даёт `STRICT`. Запись, нарушающая уникальность, отклоняется. Такой индекс заодно служит целью для `ON CONFLICT (...)` и условием совпадения в `MERGE`.

### BITMAP — только по явной команде

Битовый индекс включается **исключительно** оператором `CREATE BITMAP INDEX`. Через YAML-конфигурацию его включить нельзя, и сам по себе он не появится: молча менять структуру индекса под данными система не будет.

Ограничения и область применения:

- Только **одна колонка**. `CREATE BITMAP INDEX ... (a, b)` отклоняется.
- Имеет смысл при **малой мощности** — десятки различных значений: флаги, статусы, регионы, типы событий.
- На колонке высокой мощности (идентификаторы, метки времени, электронная почта) bitmap проигрывает B+ дереву и по памяти, и по скорости.

```sql
CREATE BITMAP INDEX idx_orders_status ON orders (status);   -- 5 статусов: уместно
CREATE BITMAP INDEX idx_orders_id ON orders (id);           -- бессмысленно, берите обычный
```

## Составные индексы

Порядок колонок важен. Индекс `(a, b)` помогает запросам с условием по `a` и по `a` вместе с `b`. Запрос только по `b` его не использует.

```sql
CREATE INDEX idx_orders_cust_status ON orders (customer_id, status);

SELECT * FROM orders WHERE customer_id = 100;                      -- индекс работает
SELECT * FROM orders WHERE customer_id = 100 AND status = 'new';   -- индекс работает
SELECT * FROM orders WHERE status = 'new';                         -- индекс не подходит
```

Ставьте первой ту колонку, по которой фильтруете всегда.

### Пример

```sql
CREATE TABLE orders (
  id BIGINT PRIMARY KEY,
  customer_id BIGINT NOT NULL,
  status VARCHAR(16) NOT NULL,
  created_at TIMESTAMP NOT NULL
);
CREATE INDEX idx_orders_cust_status ON orders (customer_id, status);

-- Использует префикс составного индекса:
SELECT id FROM orders WHERE customer_id = 42 AND status = 'NEW' LIMIT 50;
-- Не использует idx_orders_cust_status (нет ведущей колонки):
SELECT id FROM orders WHERE status = 'NEW' LIMIT 50;
```

План смотрите через `EXPLAIN` — [EXPLAIN и AQE](explain-and-aqe.md).

## Первичный ключ

Отдельно индексировать первичный ключ не нужно. По нему считается шард. Равенство по **полному** первичному ключу — точечное чтение: без скана и без обращения ко вторичным индексам. Равенство только по ведущей колонке составного PK — это уже не «весь ключ»: планировщик не подменяет его точечным get по полному PK.

## Когда какой индекс берёт план

| Условие | Что ожидать |
|---------|-------------|
| EQ по полному PK | Точечное чтение по ключу |
| EQ по ведущей колонке составного вторичного индекса `(a, b)` | Префиксный путь по `(a, …)`; если есть отдельный одноколоночный / bitmap индекс на `a` и нет `ORDER BY` по `b` — план может предпочесть узкий индекс |
| EQ только по неведущей колонке | Составной индекс `(a, b)` не подходит |
| `ORDER BY` по второй колонке составного индекса при EQ по первой | Остаётся упорядоченный лист составного дерева |

Порядок сравнения фиксированной ширины INT/LONG в индексе и в остаточном фильтре — **знаковый** (`Integer.compare` / `Long.compare`), как и литералы со знаком в грамматике. Подробнее: [матрица SQL](support-matrix.md).

План смотрите через `EXPLAIN` — [EXPLAIN и AQE](explain-and-aqe.md).

## Путь запроса

Поиск по индексу идёт по трём уровням, сверху вниз:

1. **Индекс в памяти** — ускоритель горячего набора.
2. **Запечатанное дерево `.sbpt`** — неизменяемое B+ дерево фиксированных страниц на диске (формат записи **VERSION 2**, знаковое сравнение INT/LONG). Файлы **VERSION 1** (legacy unsigned) при чтении **отклоняются** — нужен reseal / `dumpDomain` после обновления.
3. **Файл данных `.gmap`** — по найденному указателю достаётся строка.

**Промах по индексу не превращается в полный скан партиции.** Если индекс отвечает «такого значения нет», запрос так и отвечает, а не начинает читать таблицу целиком.

Значения ключей на всём этом пути остаются байтами: индекс не разбирает строку в объекты, чтобы сравнить значение.

Устройство файлов — [хранение (GMAP)](../understand/storage-sealed-gmap.md).

## Обновление индекса

Индексы обновляются после того, как мутация зафиксирована в основной карте: сначала данные, потом индекс. Обновление выполняет отдельный обработчик, поэтому запись не ждёт перестроения деревьев.

Практическое следствие: индекс догоняет данные, а не опережает их. На точечных чтениях по первичному ключу это никак не сказывается.

## Долговременное хранение

После запечатывания сегмента вторичные индексы лежат в файлах фиксированных страниц (`.sbpt`, для bitmap — `.sbm`). Новый `.sbpt` пишется в **VERSION 2** (знаковое сравнение INT/LONG на диске совпадает с RAM). Файлы **VERSION 1** (беззнаковое сравнение) при открытии **отклоняются** — после обновления бинарника нужен reseal / `dumpDomain`, а не «тихое» чтение старых деревьев: [обновление узла](../configure-and-operate/operations/upgrade.md).

Индекс в памяти остаётся ускорителем горячего набора и может быть вытеснен целиком — данные не теряются, запрос сходит в запечатанный файл. При `hydrate-mode: LAZY` первый промах после рестарта платит I/O запечатанного файла; при `FULL` деревья теплее ценой более долгого старта.

Контрольная точка `index-ckpt` хранит отметку по ключам, а не полный дамп дерева.

## Сколько индексов делать

Каждый индекс — это дополнительная работа на каждой записи и дополнительная память. Здравые правила:

- Индексируйте колонки, по которым реально фильтруете в `WHERE` и соединяете в `JOIN`.
- Не плодите индексы «на всякий случай» на таблице с интенсивной записью.
- Один составной индекс часто заменяет два обычных — если порядок колонок выбран правильно.
- Перед тем как добавлять индекс, посмотрите [`EXPLAIN`](explain-and-aqe.md): возможно, план уже точечный.

Как индексы влияют на измеренную пропускную способность — [ёмкость и пороги](../performance/capacity-slo.md).
