# Журнал дефектов (`Test_G_NNNNN`)

Каждая регрессия в Grid получает номер, запись в этом журнале и тест с тем же номером. Порядок именно такой: сначала запись, потом починка и тест — иначе дефект теряется.

| Поле | Правило |
|------|---------|
| Тикет | `G-NNNNN`, номер монотонный (`00001`, `00002`, …) |
| Тест | Класс или метод `Test_G_NNNNN` (либо `@DisplayName("Test_G_NNNNN")` плюс `test_G_NNNNN_*`) в `grid-server-core/src/test/java/` |
| Запись | Идентификатор, дата, симптом, причина, починка, статус `OPEN` или `FIXED`, путь к тесту |
| Новый дефект | Берём следующий свободный номер |

## G-00001 — замена запечатанного чекпоинта при живом mmap (Windows)

| Поле | Значение |
|------|----------|
| **Статус** | FIXED |
| **Дата** | 2026-09-17 |
| **Тест** | `index.unit.replication.Test_G_00001` |
| **Симптом** | При периодическом сбросе запечатанных данных (примерно раз в 30 с) после INSERT или работы в DBeaver в логе появлялось `WARN [repl-bg] Sealed checkpoint failed: java.lang.IllegalStateException: sealed dump failed append_domain#1` |
| **Причина** | `SealedGridMapService.dumpDomain` писал и заменял `*.gmap` через `ATOMIC_MOVE` с `REPLACE_EXISTING`, пока предыдущий `SealedGridMapReader` держал файл отображённым в память. На Windows это даёт `AccessDeniedException` или `FileSystemException`. На Linux семантика unlink обычно это маскирует, поэтому дефект долго не был виден |
| **Починка** | Живой reader сначала освобождается: снимаем отображение и закрываем (`releaseReader`) **до** `writeNodes` и удаления осиротевших файлов. Дальше запись → открытие → `swapReader`. В предупреждении чекпоинта теперь логируется исходное исключение, причина не теряется |
| **Заметки** | Жёсткие гейты по запечатанным данным ослаблять нельзя. Регрессионная проверка: двойной сброс при живом reader должен проходить и на Windows, и на Linux |
