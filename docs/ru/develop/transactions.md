# Транзакции

Два сеанса, один ключ. Пока первая транзакция не закоммитила, вторая не должна видеть её грязные строки. В Grid до `COMMIT` изменения лежат только в буфере сессии; на `COMMIT` — при записи на диск — сначала журнал, потом карта. Лучше отказ, чем частично видимый коммит.

## Из чего состоит

| Часть | Роль |
|-------|------|
| `Connection` | Транспорт: один TCP-сокет |
| `TxContext` | Независимая транзакция на этом транспорте (плюс дескриптор PREPARE) |
| `SqlTxBuffer` | Грязные мутации сессии до `COMMIT` / `ROLLBACK` |
| `SqlRecordLockManager` | Честные блокировки по ключу записи `(таблица, ключ)` |
| `SqlTxCommitter` | Маркеры в OpLog и публикация в карту памяти |
| `MultiShardCommitBarrier` | Учёт участвующих потоков `таблица#шард` в одной единице commit |

Важные следствия модели:

- Открытая транзакция **не** пишет в карту памяти и не трогает ORCHID до `COMMIT`. Чужие сессии её изменений не видят.
- Свои же изменения внутри транзакции видны: `WHERE` по грязным строкам вычисляется по тем же условиям фильтра, что и по закоммиченным.
- **DDL внутри открытой транзакции отклоняется.** `CREATE TABLE`, `CREATE INDEX`, `DROP` и прочее выполняйте в autocommit, до или после транзакции. Это сознательное ограничение: каталог не участвует в откате.
- При включённом `grid.durability.enabled` коммит не продолжается при ошибке: если журнал или кворум не подтвердили запись, данные не станут видимыми и коммит завершится ошибкой.

## Клиентский вид

Опорный шаблон — `Mono.usingWhen`: ресурс (`begin()`), работа, и завершение при любом исходе.

```java
Mono<Void> transfer = Mono.usingWhen(
        connection.begin(),
        tx -> tx.createStatement("UPDATE accounts SET balance = balance - ? WHERE id = ?")
                .bind(0, 10L)
                .bind(1, 1L)
                .executeUpdate()
                .then(tx.createStatement("UPDATE accounts SET balance = balance + ? WHERE id = ?")
                        .bind(0, 10L)
                        .bind(1, 2L)
                        .executeUpdate())
                .then(tx.commit()),
        TxContext::rollback);
```

Почему именно так:

- `usingWhen` вызовет `rollback()` при ошибке в теле **и** при отмене подписки — забыть про откат невозможно.
- Ничего не блокируется. `close()`, `commit()` и `rollback()` возвращают `Mono<Void>`; `.block()` внутри библиотечного кода и на Netty / Reactor / потоке-носителе virtual thread запрещён — он останавливает event loop или закрепляет носитель.
- Если нужен «доделать при любом исходе» побочный эффект, добавляйте `doFinally`, а не `try/finally` с блокировкой.

Если транзакция дошла до `commit()`, `rollback()` в release-фазе уже не навредит: сессия закрыта, откатывать нечего.

Пакетный вариант, когда несколько запросов делят одну транзакцию и один RTT:

```java
tx.executeBatch(List.of(
        "UPDATE accounts SET balance = balance - 10 WHERE id = 1",
        "UPDATE accounts SET balance = balance + 10 WHERE id = 2"));
```

Все запросы батча видят один и тот же грязный буфер; при ошибке остаток не выполняется.

## Параллельные транзакции

Несколько `connection.begin()` на одном соединении дают несколько независимых транзакций. Есть **два** потолка — их нельзя путать:

| Потолок | Где | По умолчанию | Роль |
|---------|-----|--------------|------|
| Клиентский `maxTxContexts` | URL / `ConnectionOptions` | **256** | Мягкий предел логических сессий, которые клиент откроет на одном TCP |
| Серверный канал | SQL TCP listen (`SqlServer`) | **8** | Жёсткий предел на принятый канал; Boot **не** прокидывает `grid.sql.max-tx-contexts` |

Если сервер отвечает `maxTxContexts=8 exhausted`, откройте ещё один `Connection` — Boot не поднимает потолок слушателя из `grid.sql.max-tx-contexts`. Подробнее: [SQL-сервер](../configure-and-operate/configuration/sql-server.md).

Это не пул JDBC: не заводите N соединений, чтобы получить N транзакций. Изоляция между ними держится на блокировках записей, маркерах `TX_*` в журнале и дескрипторе PREPARE, а не на отдельных TCP-каналах.

## Точки сохранения

```java
Mono<Void> partial = Mono.usingWhen(
        connection.begin(),
        tx -> tx.createStatement("UPDATE t SET v = 1 WHERE id = 1").executeUpdate()
                .then(tx.savepoint("s1"))
                .flatMap(sp -> tx.createStatement("UPDATE t SET v = 2 WHERE id = 2").executeUpdate()
                        .onErrorResume(err -> tx.rollbackTo(sp).then(Mono.just(0L))))
                .then(tx.commit()),
        TxContext::rollback);
```

`savepoint` / `rollbackTo` / `release` работают только внутри открытой транзакции и только в памяти — журнал и ORCHID они не трогают. Последовательности (sequences) при откате к точке сохранения не отматываются.

## Блокировки

Блокировки берутся по ключу записи через `SqlRecordLockManager`: честная очередь на `(таблица, ключ)`. Ожидание происходит на virtual-thread логики, не на Netty event loop.

`FOR UPDATE` и `SKIP LOCKED` выполняются **только на пишущем узле** — реплика только для чтения такой запрос отклоняет. При включённой репликации агенты блокировок на соседних узлах берутся из **`peers` репликации** (не из `grid.sql.distributed-peers` — тот ключ для разлёта только чтения SELECT/JOIN); те же индексные ключи в сериализованных байтах блокируются у соседей через `DistForUpdateCoordinator`. Ошибка Netty на блокировке соседа — **отказ клиенту**, не тихий только-локальный commit. Без агентов — только локально. Multi-table / INNER JOIN `FOR UPDATE` поддерживается. Голосование prepare/commit-dec для блокировок на соседних узлах — продукт (2PC-lite), не внешний XA. Подробнее: [чтение с реплики](../configure-and-operate/operations/replica-reads.md).

Типовой сценарий очереди:

```sql
BEGIN;
SELECT id, payload FROM outbox WHERE status = 'NEW' ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED;
-- обработка
UPDATE outbox SET status = 'DONE' WHERE id = ?;
COMMIT;
```

## PREPARE

`PREPARE name AS <sql>` / `EXECUTE name(...)` / `DEALLOCATE name` разбираются только через ANTLR-грамматику `SimplifiedSql.g4`; тело берётся из интервала исходного текста, поэтому пробелы и регистр сохраняются. На клиенте есть обёртка `connection.prepare(name, bodySql)` → `PreparedHandle` с `bind(...)` / `execute()`.

`PREPARE` — операция writer-сессии, на реплику она не маршрутизируется.

## Несколько шардов и несколько ЦОД

Коммит-юнит собирается по участвующим потокам `таблица#шард`: `MultiShardCommitBarrier` открывает все потоки, пропускает операции и закрывает их вместе, а при ошибке в середине откатывает уже открытые.

Это **локальный барьер на пишущем узле**, а не полный XA 2PC поверх чужих ресурс-менеджеров. Dist `FOR UPDATE` может брать **блокировки строк на соседних узлах** и использовать каркас prepare/commit-dec (`DistForUpdatePrepareVotes`), когда агенты подключены — это всё ещё не внешний XA-координатор.

Для Cross-DC используется членство конверта TX (`TxEnvelopeCoordinator`): состав потоков транзакции пишется в маркер `TX_BEGIN`, а отправка на удалённую площадку и публикация в удалённой карте происходят только после коммита всех потоков конверта. То есть удалённо не может стать видимой половина транзакции.

Практическое следствие: держите транзакцию в пределах одного логического набора ключей. Чем больше шардов в одном коммит-юните, тем длиннее барьер и тем дороже откат.

## Что не стоит делать

- Открывать транзакцию «на всякий случай» и держать её на время сетевого вызова во внешнюю систему — блокировки записей держатся ровно столько же.
- Ждать `FOR UPDATE` на реплике: получите отказ, а не чтение.
- Считать `maxTxContexts` числом соединений или заводить под каждую транзакцию свой сокет.
- Вызывать `.block()` на `commit()` / `rollback()` внутри сервисного кода — только на границе приложения (`main`, CLI, тест).
