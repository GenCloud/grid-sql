# Потоковая выдача результатов

Большая выборка не приезжает целиком одним ответом. Клиент и сервер работают окнами: сервер отдаёт порцию строк и останавливается, пока клиент не попросит следующую. Это встроено в основной протокол, а не надстройка вроде JDBC-курсора.

## Как это выглядит по протоколу

Протокол — кадры с длиной в начале (little-endian) со собственными опкодами. Для одной выборки последовательность такая:

| Фрейм | Направление | Смысл |
|-------|-------------|-------|
| `EXEC` | клиент → сервер | SQL плюс параметры, со своим `requestId` |
| `ROW_DESC` | сервер → клиент | Описание колонок; клиент получает `Result` с метаданными |
| `ROW_DATA` | сервер → клиент | Строки текущего окна |
| `FETCH(n)` | клиент → сервер | Запрос следующих `n` строк по тому же `requestId` |
| `EXEC_DONE` | сервер → клиент | Выборка закончилась, портал закрыт |
| `CANCEL` | клиент → сервер | Бросить портал и прекратить выдачу |
| `ERROR` | сервер → клиент | Ошибка выполнения |

Сервер держит открытые порталы в `SqlExecHandler`, ключ — `requestId` того же `EXEC` (или `BATCH_EXEC`). Первое окно уходит сразу после `ROW_DESC`; дальше сервер ждёт `FETCH`. `CANCEL` идемпотентен: после дренажа портала или повторного вызова он просто подтверждается, утечки записей не остаётся.

Максимальный размер фрейма — 16 МиБ. Это ограничение на один фрейм, а не на размер выборки: строки ходят окнами.

## Размер окна

| Уровень | Значение |
|---------|----------|
| Первое окно сервера | 64 строки |
| Последующие `FETCH` | `min(запрошенный Reactor demand, fetchWindow)` |
| `fetchWindow` по умолчанию | 64 |
| Настройка на соединении | опция URL `?fetchWindow=256` |
| Настройка на запросе | `statement.fetchWindow(256)` |

То есть окно — это **потолок**, а не фиксированный размер: если подписчик запросил меньше, клиент и попросит меньше. Обратное давление Reactor напрямую превращается в размер `FETCH`.

```java
Flux<Order> orders = connection
        .createStatement("SELECT id, customer_id, total FROM orders WHERE total > ?")
        .bind(0, 1000L)
        .fetchWindow(512)
        .execute()
        .flatMap(result -> result.map((row, meta) -> new Order(
                row.get("id", Long.class),
                row.get("customer_id", Long.class),
                row.get("total", Long.class))));
```

Как выбирать окно:

- Мелкие строки, много строк — окно больше (256…1024): меньше круговых задержек.
- Широкие строки или большие BLOB — окно меньше: иначе одно окно распухает в памяти и на канале.
- Если потребитель медленный (пишет в другую систему), не гонитесь за большим окном: строки просто будут ждать в буфере клиента.

## Отмена

```java
Flux<Order> firstPage = orders.take(100);
```

`take`, `timeout`, отмена подписки сверху — всё это приводит к `CANCEL` по протоколу: сервер бросает портал, остаток выборки не считается и не кодируется. Прямой вызов `Result.cancel()` делает то же самое; на незапущенном или уже завершённом потоке это ничего не делает.

Практический смысл: «первые N строк большой выборки» стоит именно N строк работы сервера, а не полной материализации.

## Типичные ошибки

| Ошибка | Что происходит |
|--------|----------------|
| Клиент не шлёт `FETCH` после первого окна | Портал висит, сервер ждёт; соединение занято |
| Окно слишком большое на широких строках | Пик памяти и длинные фреймы ближе к 16 МиБ |
| Игнорируют отмену подписки | Сервер продолжает считать остаток, пока клиент «уже ушёл» |
| Путают коррелятор `requestId` с пулом TCP | Открывают лишние сокеты вместо нескольких `TxContext` на одном |

## Корреляция запросов, а не пул соединений

На одном TCP-сокете одновременно идут несколько запросов. Клиентский `SqlClientInboundHandler` (`org.genfork.grid.sql.client.transport`) держит карту `requestId → ожидающий обмен` и по ней раскладывает входящие фреймы. Эта карта — **коррелятор**, а не пул простаивающих соединений и не «прогретые слоты». Реактивный и синхронный фасады (`JdbcSync` / `SyncAwait`) делят этот пакет транспорта.

Отсюда два следствия:

- `maxTxContexts` на клиенте — мягкий потолок логических сессий на сокете (по умолчанию **256**); на сервере жёсткий потолок **8** на TCP. Это не размер пула TCP-соединений.
- Параллельные выборки на одном соединении нормальны: у каждой свой `requestId` и свой портал.

`BATCH_EXEC` работает по той же схеме: N запросов за один RTT, результаты приходят по порядку на одном `requestId`, и у активного запроса внутри батча тот же путь `FETCH` / `CANCEL`.

## Что происходит на сервере

`SqlEngine` выполняет запрос, а Netty-слой кодирует ячейки LE-тегами. Внутри движка строки хранятся как байты: ключи и значения в фильтрах, соединениях и индексах — `byte[]` / `WireSpan` поверх бинарной записи. Декодирование в Java-объекты происходит только на самой границе — когда формируется строка результата для клиента.

Поэтому не стоит просить у движка «всю таблицу целиком в память приложения»: потоковая выдача дешевле на обеих сторонах.
