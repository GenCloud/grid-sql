# DDL

DDL changes the catalog: `TableCatalog` and `TableSchema`. Parsing is ANTLR (`SimplifiedSql.g4`), execution is `SqlDdlExecutor`.

One rule to remember up front: **DDL inside an open transaction is rejected**. `COMMIT` or `ROLLBACK` first, then change the schema. The catalog does not take part in rollback, so it never enters the transactional buffer.

Object names are unquoted words — ASCII letters, digits and underscore, matched case-insensitively, optionally qualified as `schema.object`. There are no double-quoted identifiers, so a column cannot carry a keyword as its name. The full accepted syntax is in the [support matrix](support-matrix.md).

## CREATE TABLE

```sql
CREATE TABLE IF NOT EXISTS orders (
  id          BIGINT PRIMARY KEY,
  customer_id BIGINT NOT NULL,
  total       DOUBLE,
  status      VARCHAR,
  created_at  TIMESTAMPTZ
);
```

`IF NOT EXISTS` makes the statement repeatable: if the table already exists, the statement succeeds without an error and without changes. That is convenient for bootstrap scripts that run on every application start.

For column types see [types](types.md).

### Primary key

A primary key is effectively mandatory: it determines the shard and drives point lookups. There are two ways to declare it.

```sql
-- on the column
CREATE TABLE users (id BIGINT PRIMARY KEY, email VARCHAR);

-- composite, as a separate table element
CREATE TABLE order_items (
  order_id BIGINT,
  line_no  INT,
  sku      VARCHAR,
  PRIMARY KEY (order_id, line_no)
);
```

Primary key columns take part in shard computation. A query with equality on the full key becomes a point read instead of a scan.

### Auto-increment

Two forms, both ending in a server-generated value:

```sql
CREATE TABLE events (
  id   BIGSERIAL PRIMARY KEY,
  body VARCHAR
);

CREATE TABLE tickets (
  id   BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  note VARCHAR
);
```

`SERIAL` gives `INT`, `BIGSERIAL` gives `BIGINT`. `GENERATED BY DEFAULT AS IDENTITY` means: if a value is supplied explicitly it is used; otherwise the next one is generated.

### NOT NULL

```sql
CREATE TABLE accounts (
  id      BIGINT PRIMARY KEY,
  owner   VARCHAR NOT NULL,
  balance DOUBLE
);
```

A column without `NOT NULL` accepts `NULL`. Inserting `NULL` into a `NOT NULL` column is rejected.

## Constraints

### FOREIGN KEY

```sql
CREATE TABLE order_lines (
  id       BIGINT PRIMARY KEY,
  order_id BIGINT NOT NULL,
  sku      VARCHAR,
  CONSTRAINT fk_order FOREIGN KEY (order_id) REFERENCES orders (id)
    ON DELETE CASCADE
    ON UPDATE RESTRICT
);
```

Referential integrity is checked when a child row is inserted or updated: the parent must exist. Actions on parent delete and update:

| Action | Behaviour |
|--------|-----------|
| `RESTRICT` | The operation on the parent is rejected while child rows exist |
| `CASCADE` | Child rows are deleted or updated along with the parent |
| `SET NULL` | Referencing columns in child rows are set to `NULL` |

Naming the constraint with `CONSTRAINT` is optional, but it makes error messages much easier to read.

### CHECK

```sql
CREATE TABLE payments (
  id     BIGINT PRIMARY KEY,
  amount DOUBLE,
  CONSTRAINT positive_amount CHECK (amount > 0)
);
```

A `CHECK` expression is an ordinary boolean expression of the dialect: comparisons, `AND`/`OR`/`NOT`, `BETWEEN`, `IN`, `IS NULL`. It is evaluated on every row mutation.

### Uniqueness

There is no standalone column-level `UNIQUE`. Uniqueness is declared with an index:

```sql
CREATE UNIQUE INDEX uq_users_email ON users (email);
```

Details in [indexes](indexes.md).

## Indexes

```sql
CREATE INDEX idx_orders_customer ON orders (customer_id);
CREATE INDEX idx_orders_cust_status ON orders (customer_id, status);
CREATE BITMAP INDEX idx_orders_status ON orders (status);

DROP INDEX idx_orders_customer ON orders;
```

A single column gives a B+ tree of pointers, several columns give a composite tree. `BITMAP` is enabled **only** by an explicit `CREATE BITMAP INDEX` and only on one column; it cannot be turned on through YAML configuration. When bitmap is appropriate and how an index takes part in the plan — see [indexes](indexes.md).

## ALTER TABLE

```sql
ALTER TABLE orders ADD COLUMN channel VARCHAR;
ALTER TABLE orders ADD CONSTRAINT total_nonneg CHECK (total >= 0);
ALTER TABLE orders DROP COLUMN channel;
```

For existing rows an added column reads as `NULL` — no data rewrite is needed. Column type changes and renames are not supported.

## DROP TABLE

```sql
DROP TABLE IF EXISTS orders;
```

Removes the schema, the data and the table's secondary indexes.

## Schemas

```sql
CREATE SCHEMA IF NOT EXISTS analytics;
SET SCHEMA analytics;
DROP SCHEMA analytics RESTRICT;
```

A table name may be qualified: `analytics.orders`. `DROP SCHEMA` requires `RESTRICT` — there is no cascading schema drop.

## Sequences

```sql
CREATE SEQUENCE IF NOT EXISTS order_seq START WITH 1000 INCREMENT BY 1;

SELECT NEXTVAL('order_seq');
SELECT CURRVAL('order_seq');

UPSERT INTO orders (id, status) VALUES (NEXTVAL('order_seq'), 'new');

DROP SEQUENCE IF EXISTS order_seq;
```

The `RECLAIM` modifier allows freed values to be reused — useful where identifier density matters more than strict monotonicity.

## Views

```sql
CREATE VIEW active_orders AS
  SELECT id, customer_id, total FROM orders WHERE status = 'active';

CREATE MATERIALIZED VIEW daily_totals AS
  SELECT customer_id, SUM(total) FROM orders GROUP BY customer_id;

REFRESH MATERIALIZED VIEW daily_totals;

DROP VIEW IF EXISTS active_orders;
```

A plain view is inlined into the query. A materialized view stores the result and is updated by `REFRESH`; there is no automatic refresh.

## Functions and triggers

A function is bound to a Java class and method. No execution of a code string:

```sql
CREATE FUNCTION normalize_email(value VARCHAR) RETURNS VARCHAR
  AS CLASS 'com.example.GridFunctions' METHOD 'normalizeEmail';

DROP FUNCTION IF EXISTS normalize_email;
```

A trigger declares when it fires and a body written as a SQL string where `OLD.col` and `NEW.col` are available:

```sql
CREATE TRIGGER audit_orders AFTER UPDATE ON orders
  FOR EACH ROW
  WHEN 'NEW.status != OLD.status'
  AS 'UPSERT INTO order_audit (id, status) VALUES (NEW.id, NEW.status)';

DROP TRIGGER IF EXISTS audit_orders ON orders;
```

## Users and privileges

```sql
CREATE USER reporting PASSWORD 'secret';
ALTER USER reporting PASSWORD 'rotated';
GRANT SELECT ON SCHEMA analytics TO reporting;
REVOKE INSERT, UPDATE ON TABLE orders FROM reporting;
DROP USER reporting;

CREATE ROLE readers;
GRANT SELECT ON TABLE orders TO ROLE readers;
GRANT ROLE readers TO reporting;
DROP ROLE readers;
```

The privilege set is `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `DDL`. The target is a schema or a table. Roles hold privileges; `GRANT ROLE … TO user` attaches membership (checked on authorize).

`REVOKE … FROM user` drops privileges from a user. There is no separate `REVOKE ROLE`: remove membership with `DROP ROLE`. On disk: `{grid.sql.data-dir}/catalog/privileges.meta`. Operators: [security](../configure-and-operate/operations/security.md).

## What gets rejected

| Form | Why |
|------|-----|
| Any DDL inside an open transaction | The catalog changes outside the transactional buffer |
| The `JSONB` type | Use `JSON` or `VARCHAR` — it is opaque UTF-8 text |
| An unknown type token | The allowed list is in [types](types.md) |
| `ALTER TABLE ... ALTER COLUMN TYPE`, renames | Not supported: recreate the table |
| Column `DEFAULT <expression>` | Defaults come from the application or from `IDENTITY`/`SERIAL` |
| `CREATE BITMAP INDEX` over several columns | Bitmap is single-column only |
| `DROP SCHEMA` without `RESTRICT` | There is no cascading schema drop |
| Partial indexes, expression indexes | Only columns are indexed |
| `ALTER TABLE … DROP CONSTRAINT` | Constraints are dropped by recreating the table |
| A double-quoted identifier | Names are unquoted words only |

A parse error or a catalog validation error means the statement did not apply at all. There is no such thing as partially applied DDL.

## Schema changes and clients

Every schema change bumps the schema version counter (`ServerMeta.schemaEpoch`). Clients notice the new counter and re-read column metadata. No explicit reconnect is required.
